# S4 — Fill a 3-row manifest while two unrelated Gemini conversations are already open

Paths below use `projects/<name>/images/image_prompts.json`; `<name>` is the real
project folder and is substituted verbatim into every command. Nothing here is
executed against another path.

---

## 0. Why the user's two tabs cannot become one of my rows

This is the whole scenario, so it is settled before the first command, not
after. The isolation is structural — it does not depend on my noticing anything
about the two open conversations:

1. **Identity is the bridge session, never the page.** Row *n* runs under session
   `ppt-master-image-{n}`; the bridge scopes its "current tab" to the session, so
   each slot is a handle on one tab nothing else can move. The user's two
   conversations belong to no bridge session, so no slot command can ever resolve
   to them. Which tab holds which row is the **slot number** — never inferred
   from a URL, a title, or page text, both of which the user's tabs also have.
2. **Every slot tab is created, never adopted.** `submit()` opens the tab with
   `navigate {"url": "https://gemini.google.com/images", "newTab": true}` on the
   slot session. A brand-new tab cannot be a pre-existing conversation.
3. **`find_tab` is never used** — not by the script, not by me, not for
   diagnosis. It is the only operation that would go looking through the browser
   for a matching tab, and it returns `"ok": true` without switching; a
   collection loop built on it once wrote one image under four file names. In
   this scenario it is also exactly the tool that would hand me a stranger's
   conversation.
4. **No slot is navigated after submit**, and no non-slot tab is navigated at
   all. Every `evaluate` / `snapshot` / `click` / `fill` is addressed to a slot
   session and therefore lands on that session's own tab.
5. **`require_daemon()` reads, it does not claim.** It sends `list_tabs` on the
   bare `ppt-master-image` session — a read that moves nothing. That bare name is
   not a slot name (slots are `-1`…`-3`), so it cannot collide with one either.
6. **Cleanup targets sessions, not titles.** `close_tab` on
   `ppt-master-image-1..3` only. I never close a tab matched by URL or title,
   which is the one cleanup shape that could take out the user's work.
7. **Proof after the fact:** distinct checksums across the three outputs (§8.3).
   Two identical files would mean isolation broke, and the run is redone rather
   than patched.

One accepted, unavoidable overlap: `~/Downloads`. Slot downloads are matched by
`Gemini_Generated_Image_*` with mtime newer than that row's click, so files
already sitting there are safe — but a Gemini image the *user* saves by hand
during the run would be inside that window and could be picked up or cleared. I
inventory `~/Downloads` first (§2) and ask the user not to download from their
two conversations while the run is going.

## 1. Preconditions (§2), checked without touching the user's tabs

| Requirement | How I establish it here |
|---|---|
| WebBridge daemon | `require_daemon()` inside the script — `list_tabs` on `ppt-master-image`. If it fails the script raises with the "not answering on 127.0.0.1:10086" message and I stop there. |
| Gemini signed in | Proven by row 1's own fresh tab: a signed-out page has no prompt box, so `prompt box never appeared` is the signal. I do **not** verify by inspecting the user's open conversations — that is the confusion this scenario forbids. |
| Browser UI in Korean | Same probe. The five matched names are `Gemini 프롬프트 입력`, `메시지 보내기`, `사용해 보기`, `원본 크기 이미지 다운로드`, `닫기`. If the UI is not Korean I stop; I do not guess replacements. |
| Manifest | Read locally (§2), no browser. |
| Downloads land silently | Optional. If they don't, the run still finishes at the displayed size and says so. |

If any precondition fails I stop and name it. I do **not** fall back to another
image path from inside this skill — that decision belongs to the caller.

## 2. Pre-flight, local only

```bash
ls -la ~/Downloads/Gemini_Generated_Image_* 2>/dev/null || echo "no pre-existing Gemini downloads"
```

Records what was already there, so the post-run "no leftovers" check (§8.5) is
about my run and not about the user's earlier work.

```bash
python3 -c "
import json
d = json.load(open('projects/<name>/images/image_prompts.json'))
for i, r in enumerate(d['items']):
    print(i, repr(r.get('status')), repr(r.get('source') or r.get('type')),
          repr(r.get('aspect_ratio')), r.get('filename'), 'slot=', r.get('slot'))
"
```

What I check and the branch each outcome takes:

- **Statuses.** Only `Pending` / `Failed` are taken. `Generated` is skipped and
  `Needs-Manual` belongs to the user and is never submitted. With three rows and
  `--batch` defaulting to 10, whatever is retryable goes in a single pass.
- **Every retryable row is an `ai` row.** The script selects on status alone, so
  a non-`ai` `Pending` row would be sent to Gemini as a prompt. If I see one I
  stop and ask the caller rather than editing their manifest.
- **`aspect_ratio` and `prompt` exist and are well formed** (`"16:9"`, `"4:3"`,
  `"1:1"`). A missing key crashes `submit()` mid-run with tabs already open; a
  malformed ratio makes `aspect_ratio_value()` return `0.0`, which silently
  suppresses the `** ratio off` warning. Either one is fixed or raised before I
  start, not after.
- **Stale `slot` values** from an earlier interrupted run. Harmless for a
  submitting run (submit overwrites `slot`), but I note them so I don't later
  mistake a stale number for one of this run's.
- **The `prompt` text must not already contain a ratio sentence** — the script
  prepends one (§4), and I do not add a second by hand.

## 4. The run

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

Every flag left at its default, deliberately:

- **No `--batch`.** Default 10 ≥ 3, so all three submit in one pass. Splitting
  would only repeat the serial submission cost. Lowering `--batch` is for the
  unusual-traffic challenge, and there is no evidence of one yet.
- **No `--displayed-size`.** Three rows of originals fit easily: ~10s serial
  submit per row plus ~12s serial download per row plus generation that overlaps
  (rows typically ready 20–50s after submit) — the measured 2-row run of
  originals was 81s end to end. Resolution is worth more than the ~12s/row here.
- **No `--deadline`.** 300s is far more than the ~100–130s this shape implies.
- **No `--generate-wait`.** 10s is fine; sweeping early costs one cheap probe.
- **No `--output`.** Images land in the manifest's own folder, which is the
  `images/<filename>` contract Step 6 of ppt-master reads.
- **No `--collect-only`.** These rows have not been submitted yet.

### 4.1 What submission does per row, and how the ratio rides along

For batch index `i` (0-based, over the retryable rows in manifest order), session
= `ppt-master-image-{i+1}`:

1. `navigate {url: .../images, newTab: true}` on that session. `/images` and
   never `/app` — `/images` runs the image model and takes a bare prompt; the
   chat surface may answer with text. One retry after 2s if the navigate returns
   not-ok, then the row is given up on.
2. Up to 15 jittered snapshot passes (1.4–2.6s): if `사용해 보기` is present the
   onboarding dialog is dismissed and the pass repeats; otherwise the
   `Gemini 프롬프트 입력` textbox ref is captured.
3. **The prompt carries its own row's ratio in its first line**, because the page
   exposes no aspect-ratio control. The script builds
   `"Generate a {ar} image (aspect ratio exactly {ar}).\n\n" + item["prompt"]`
   from that row's `aspect_ratio` — so row 1 might send a 16:9 header, row 2 a
   4:3 header, row 3 a 1:1 header, each from its own field, into its own tab.
   Measured returns: 16:9 → 2752x1536, 4:3 → 2400x1792, 1:1 → 2048x2048. I never
   hand-edit the ratio into the prompt, and never reuse one row's header for
   another.
4. `fill` the box with that text, pause 0.5–1.4s (a person reads what they
   typed), then poll up to 10 jittered snapshots for `메시지 보내기` — the send
   button only renders once the box holds text — and **click it. Never Enter**;
   the bridge has no key-press tool.
5. **Verify the send actually took**, because the bridge reports success for
   actions it did not perform. `SUBMITTED_JS` requires *both* a `/app/`
   conversation URL *and* the answer having started (`Creating your image`, or a
   `blob:` image). A conversation URL alone is not proof. Up to 9 jittered
   checks; on failure one refill-and-resend, then the same check again.
6. On success, `item["slot"] = i` is written into the manifest and I copy the
   mapping into my own notes as well: `filename ↔ slot i ↔ session
   ppt-master-image-{i+1}`. Slot is the *batch index*, so a row whose submit
   failed does not shift the numbers of the rows after it. I keep this note
   because a successful save pops `slot` from the manifest, and §7's recovery
   branches need it.
7. Jittered 1.0–2.6s gap before the next row. Every wait in the run is jittered;
   metronomic pacing is a machine signature and preceded Google's challenge.

Rows that fail to submit get no `slot`, stay `Pending`, and are handed to §7.4.

## 5. How a finished image is read out of its own tab

After submitting, the run settles 10s, then sweeps — it never blocks on one row.
All remaining slots are probed **concurrently** each sweep, and a slot still
generating is skipped and looked at again next sweep (jittered 3.5–7.0s). Waiting
out one slow row in place is what once spent the budget the others needed and
reported two finished images as failures.

Per slot, per sweep, `READY_JS` on that slot's session only:

- Finds the first `<img>` whose `src` starts with `blob:`.
- If `naturalWidth < 300`, **forces the decode**: `img.loading = 'eager'`,
  `scrollIntoView({block:'center'})`, and `img.decode()`. Scrolling alone is not
  enough — the result is routinely laid out at zero size, and `scrollIntoView` on
  a zero-box element is a no-op, so the lazy decode never fires and the row polls
  until the deadline.
- Returns four facts: `present`, `creating`, `finished` (Gemini's clock),
  `decoded` (ours). Keeping the last two apart is what lets a slow row be
  attributed to generation rather than to detection.
- `alive = present || creating`. A slot that is neither for more than 75s is
  **empty, not slow**: `last_error` is set, its `slot` is popped so a later
  `--collect-only` is not pointed at a blank tab, and it stops spending budget.

When `decoded` is true, `export_to()` reads the image out of that same tab:

1. **Open the viewer first.** There is no download button beside the inline
   result: the result `<img>` sits inside a `<button class="image-button">`, and
   only after clicking it do `이미지 공유` / `이미지 복사` /
   `원본 크기 이미지 다운로드` exist. Skipping this is why earlier runs silently
   saved 1024px canvas copies.
2. Poll up to 7 jittered snapshots for `원본 크기 이미지 다운로드` (the viewer
   animates in), then click it.
3. **Give the download real time.** Up to 25×1s waiting for a
   `~/Downloads/Gemini_Generated_Image_*` newer than the click — the click's
   return value proves nothing; only the file does. Then wait for its size to
   stop changing (up to 8×1s), because a multi-megabyte PNG is still growing when
   it first appears and one comparison a second apart reads that as a refusal.
4. Copy the bytes to `projects/<name>/images/<filename>`, clear **every**
   `Gemini_Generated_Image_*` newer than the click (one click can produce more
   than one file, and a partial left behind is read as the next row's file), and
   close the viewer with `닫기` so the next probe sees the page as it was.
5. Fallbacks, kept apart on purpose: *viewer never opened* is that row's bad luck
   alone and the next row still gets its chance at the original; *the control was
   clicked and no file arrived* is the browser refusing, which it will do for
   every row, so the wait is dropped for the rest of the run. Either way the
   canvas readback yields the 1024px displayed copy and the row is named in the
   final `**` line.
6. The saved file's real dimensions are compared to that row's `aspect_ratio`;
   drift above 4% prints `** ratio off`. Status becomes `Generated`, `last_error`
   and `slot` are dropped, and **the manifest is written immediately** — so an
   interrupted run keeps what it finished.

| `sweep N: K still generating` | Normal; K should fall. |

| `the browser refused the download` | §7.6, all later rows. |
| `** N of M row(s) fell back to the 1024px rendered copy` | Absence of this line is the pass for check 4. |
| `saved 3 this run · manifest 3/3 · Ns elapsed (within the 300s deadline)` | Target end state. |

## 7. Decision points and the branch I take

**7.1 Daemon not answering.** The script raises before touching the browser. I
stop, name the precondition, and hand back. No other image path is chosen here.

**7.2 `prompt box never appeared` on row 1 / on every row.** Before blaming the
UI language I read that slot's own URL — `evaluate` of `location.href` on
`ppt-master-image-1`, never `find_tab`, never a look at the user's two tabs.
- `google.com/sorry/index…` → Google's unusual-traffic challenge. I stop, tell
  the user, and let them clear it in the browser. I do not attempt to answer it.
  Already-generated tabs are unaffected; only new navigations are, so after they
  clear it I resubmit only the rows that never went out.
- Otherwise → signed out, or a non-Korean UI. Both look identical in the log,
  which is why the URL was read first. Stop and name the precondition.

**7.3 The challenge appears mid-run** (later rows suddenly fail while earlier
rows are fine): same handling, plus lower `--batch` on the retry — three rows is
already well under the ten-tab shape that tripped it once.

**7.4 A row's send never took, or a row went dead (>75s with nothing).** It stays
`Pending` with no `slot`. Fix: re-run the exact same command (not
`--collect-only` — there is no tab to collect from, and a row without a slot is
resubmitted rather than guessed). The rerun renumbers slots from 0 over whatever
is still retryable and opens fresh tabs; that is safe precisely because slots are
only ever created, never matched against existing tabs. I close nothing first.

**7.5 `viewer never opened` → one row at 1024px.** The row is already saved and
marked `Generated`, and its `slot` has been popped — so `--collect-only` alone
would answer "no recorded slot … Resubmit them instead". To get the original from
the tab that still holds it I edit that one row back to `"status": "Failed"` and
restore `"slot": <the index from my §4.1 notes>`, then:
```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json --collect-only
```
If I do not have that index with certainty, I resubmit the row instead of
guessing a slot — a wrong number reads another row's tab.

**7.6 `the browser refused the download` → every later row at 1024px.** That is
the browser's automatic-downloads setting for `gemini.google.com`, not something
I change myself. I either report the run as delivered at the displayed size, or
ask the user to allow it and then redo the affected rows by the §7.5 repair.

**7.7 `** ratio off` on a row.** Not a footnote — a resubmit. Set that row's
status back to `"Failed"` (no flag redoes a `Generated` row) and re-run the plain
command so it gets a fresh tab and a fresh prompt with its ratio header.

**7.8 Deadline expires with rows unread.** Their tabs still hold their images and
their slots are recorded, so nothing is regenerated: re-run with
`--collect-only`. I do **not** close any tabs before this, and I do not lower
`--batch` on this evidence.

**7.9 Two output files share a checksum.** Slot isolation broke — the exact
failure this scenario is about. I do not patch it: both rows go back to `Failed`,
their `slot` values are cleared, and the affected rows are resubmitted into fresh
tabs. `--collect-only` is not used, since the mapping that produced the duplicate
cannot be trusted.

**7.10 Anything left `Pending` at the end** is handed back to the caller with its
`last_error`. The manifest is the record.

## 8. Verification before I report success

```bash
python3 -c "
import json
d = json.load(open('projects/<name>/images/image_prompts.json'))
for r in d['items']:
    print(r['status'], r['filename'], r['aspect_ratio'], r.get('slot'), r.get('last_error',''))
"
ls -l projects/<name>/images/*.png
shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
python3 -c "
import pathlib, struct
for p in sorted(pathlib.Path('projects/<name>/images').glob('*.png')):
    b = p.read_bytes()[:24]
    w, h = struct.unpack('>II', b[16:24])
    print(p.name, w, h, round(w/h, 3))
"
ls ~/Downloads/Gemini_Generated_Image_* 2>/dev/null || echo "no leftovers"
```

1. All three requested rows read `Generated` and their files exist.
2. Each file's ratio is within 4% of its own row's `aspect_ratio` — and the file
   whose ratio matches row 2 is the one named for row 2. Mismatched pairing, not
   just a bad ratio, is the symptom that would betray a crossed tab.
3. No two of the three files share a checksum. Identical files mean isolation
   broke → §7.9.
4. No file is 1024px on its long edge (I did not ask for `--displayed-size`), and
   the run printed no `**` fallback line.
5. `~/Downloads` holds no `Gemini_Generated_Image_*` beyond whatever the §2
   inventory already recorded as the user's.

## 9. Cleanup, offered not assumed

Only after all three rows read `Generated` — a `--collect-only` rerun needs those
tabs, so nothing is closed while a row is still open.

I offer, and act only on a yes: post a `close_tab` command to the bridge once per
slot session — `ppt-master-image-1`, `-2`, `-3` — each body written to a file and
posted as `--data-binary @file`, the way every bridge body in this run is sent.
Three sessions, three tabs, three groups gone. I close **by session only**; I
never close a tab matched on URL or title, which is the one cleanup that could
reach the user's two conversations.

Final report to the caller: three files with their dimensions and ratios, the
manifest at 3/3, confirmation that the two pre-existing conversations were never
navigated, read, or closed, and any row that came back `Pending` with its
`last_error`.
