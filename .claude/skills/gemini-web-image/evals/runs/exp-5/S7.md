# S7 — Reading row 3's image out of a 4-row batch that is still generating

Scope: a 4-row batch has been submitted through
`.claude/skills/gemini-web-image/scripts/gemini_web_image.py`, the tabs are open,
generation is in flight, and I need row 3's image. Everything below is about how
row 3's tab is *addressed*; the extraction steps follow from it.

The whole plan rests on one sentence from §1 of the skill: **the bridge scopes its
"current tab" to the session name, so the session name is the address of the tab.**
Row 3's tab is not found, not searched for, not recognized by URL or page text. It
is named.

---

## Step 0 — What I will not do, decided up front

These are refusals, not preferences; each one is a rule in §4 of the skill.

| Never | Why |
|---|---|
| `find_tab` in any form | It returns `"ok": true` without switching tabs. A collection loop built on it wrote one image under four different file names. There is no "just to confirm" use of it. |
| `navigate` on row 3's slot | The tab already holds the answer. Re-opening the conversation is what makes the image slow to decode or bounces the tab to `/app`. |
| Reload / re-open the conversation URL | Same rule. Every reload re-fetches an image that then decodes slowly or not at all. |
| Identify the tab from `list_tabs` output, its `/app/<id>` URL, its title, or its visible prompt text | Which tab holds which row is the slot number, not something to infer. A moved tab reports its new URL, so page evidence is the one thing that cannot settle identity. |
| Re-number the surviving rows to work out row 3's slot | Re-numbering points a row at another row's tab — row 3 alone becomes slot 1 and saves row 1's image under row 3's name. |
| `close_tab` on any slot | The batch is unfinished. A `--collect-only` rerun needs those tabs. Cleanup is offered only when every row reads `Generated`. |
| Inline a bridge body on the curl command line | Non-ASCII prompt text is lost and quoting breaks. Every body goes through a file. |

---

## Step 1 — Read row 3's slot out of the manifest (this is the whole answer)

The submitted row carries `slot` in the manifest; the submission loop writes the
manifest back after the batch, so by the time generation is running the value is on
disk. I read it rather than compute it.

```bash
python3 - <<'PY'
import json, pathlib
p = pathlib.Path("projects/<name>/images/image_prompts.json")
for i, it in enumerate(json.loads(p.read_text(encoding="utf-8"))["items"]):
    print(i, it["filename"], it["status"], repr(it.get("slot")), it.get("last_error", ""))
PY
```

Two facts I take from that output, and nothing else:

1. **Which manifest entry is "row 3."** I confirm it against the filename the batch
   log reported as the third submission (`submitted <filename> (<ratio>)`). I do not
   assume row 3 is `items[2]`: the batch is `pending[:--batch]`, i.e. only the
   `Pending`/`Failed` rows, so manifest position and batch position are different
   numbers whenever any row was already `Generated` or `Needs-Manual`.
2. **That row's `slot` value.**

### Slot → session name

`slot` is the 0-based index the submission loop assigned; the session name is
`slot_name(index) = ppt-master-image-<index + 1>`. So:

| Row 3's recorded `slot` | Session that addresses its tab |
|---|---|
| `2` (the ordinary case for the third submitted row) | `ppt-master-image-3` |
| anything else | `ppt-master-image-<slot + 1>` — I use the recorded number, not 3 |

I state the off-by-one explicitly because it is the one place this can go wrong
silently. The suffix is not the row number and not the slot value; it is
`slot + 1`.

Slot values are also not guaranteed contiguous: the submission loop consumes index
`i` from `enumerate(batch)` before it knows whether `submit()` succeeded, and only
writes `item["slot"] = i` on success. A row whose submit failed leaves a hole. So
"the third submitted row" and "slot 2" are only the same thing when rows 1 and 2
both submitted cleanly — which is exactly why I read the field instead of counting.

### Branch: no integer `slot` on row 3

If row 3's entry has no `slot`, or it is not an int, then one of two things is true
and both lead to the same action:

- it was never submitted (`submit()` returned False — the log would show
  `prompt box never appeared` / `send never took` / `navigate failed twice`), or
- the sweep already dropped it as a dead row: the collector pops `slot` and sets
  `last_error` to `conversation opened but no answer ever started; resubmit this
  row` when a tab shows neither an image nor `Creating your image` for longer than
  the 75s grace.

**Branch taken: resubmit, never guess.** A row without a recorded slot has no
identifiable tab, and the skill's rule is explicit — the submitted row carries
`slot`; a row without one is resubmitted. I do *not* pick the tab that "looks like"
row 3. If `last_error` names the dead-row case I say so to the user, because that
row's tab is blank and closing/reusing it is fine, unlike the live ones.

## Step 2 — Decide *how* to read it: is the original process still running?

Row 3 is generating, so a `gemini_web_image.py` process may still be sweeping. I
check before touching anything:

```bash
pgrep -fl gemini_web_image.py
```

### Branch A — the run is still alive (most likely, given "images are generating")

**Do nothing to row 3's tab.** The running collector already sweeps every slot
concurrently every ~5s (jittered), skips whatever is still generating, and saves
each row the moment it decodes. Probing row 3 myself from a second process would
open the viewer under the collector's feet — the collector's next `READY_JS` /
`CANVAS_JS` probe reads whatever the viewer overlay leaves visible, and my
`clear_downloads_since()`-less manual download would sit in `~/Downloads` and be
read as another row's file by its newest-since test.

What I watch for in the run's log instead:

- `saved <row-3-filename> WxH ratio ... [sweep N, read at Ts]` → row 3 is done; the
  file is at the manifest's folder (or `--output`), and its status is now
  `Generated` with `slot` popped.
- `sweep N: k still generating` → still in flight, no action.
- `<row-3-filename>: extraction failed, retrying next sweep` → it stays in the
  sweep; the budget bounds the retries. No action.
- `<row-3-filename>: no answer started — dropping it` → dead row, go to Step 1's
  resubmit branch.
- `<row-3-filename>: not ready before the deadline — left Pending` → the run ended;
  go to Branch B, the tab is still open and still holds the image.

I only move to Branch B once the process has exited.

### Branch B — no run is alive

Read the open slots with the script, not by hand:

```bash
python3 /Users/jaehyeonroh/Desktop/Personal/slide-master/.claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --collect-only \
  --deadline 300
```

Why this is the right instrument even though I want one row: `--collect-only`
addresses each row by that row's own recorded `slot`, which is precisely the
addressing this scenario is about. It skips submission entirely, so nothing
navigates and nothing reloads. Rows that already finished are `Generated` and are
filtered out of `pending` before slots are built, so the sweep is effectively the
unfinished rows — row 3 among them.

Sub-branches on its output:

- `no recorded slot for <filenames> ... Resubmit them instead of collecting` naming
  row 3 → Step 1's resubmit branch.
- `nothing to collect` → every batch row either finished or lost its slot; nothing
  to read, report the manifest state.
- `saved <row-3-filename> ...` → done, go to Step 5.
- Row 3 still not ready when it exits → re-run the same command (the tabs persist),
  or raise `--deadline`. Do **not** lower `--batch` on this evidence: the one
  measurement that looked like concurrent generations slowing each other down came
  from the old broken readiness probe.

There is no `--row`/`--slot` filter, so "read only row 3" is not a flag. Collecting
the whole remaining batch is the supported single-row read, and it is harmless —
the other slots are its own tabs too.

### Branch C — I must read row 3's tab by hand

Only if Branch B is unusable (e.g. the manifest must not be rewritten right now, or
I am diagnosing rather than saving). Steps 3–4 are that path. The addressing is
identical: session `ppt-master-image-<slot + 1>`, and nothing else selects the tab.

## Step 3 — Manual probe of row 3's tab (Branch C)

Every bridge call is the same shape: a JSON body written to a file, posted to the
daemon, with `"session"` set to row 3's session. The session field *is* the tab
selection; there is no tab id, no index, no query.

```bash
cat > "$SCRATCH/probe.json" <<'JSON'
{"action": "evaluate",
 "args": {"code": "<READY_JS, pasted verbatim from gemini_web_image.py>"},
 "session": "ppt-master-image-3"}
JSON
curl -s -m 120 -X POST http://127.0.0.1:10086/command \
  -H "Content-Type: application/json" --data-binary @"$SCRATCH/probe.json"
```

(`ppt-master-image-3` above is written out for the ordinary `slot == 2` case; the
literal I actually use is whatever Step 1 produced.)

I paste the script's `READY_JS` unchanged rather than writing my own probe, because
it carries the fix the rule in §4 is about: it sets `img.loading = 'eager'`,
scrolls, and calls `img.decode()`. A read-only probe would leave a zero-box lazy
image undecoded forever — `scrollIntoView` on a zero-size element is a no-op, and a
10-row batch once stalled four rows on exactly this, three of which were finished
images reporting `naturalWidth` 0.

`READY_JS` returns four booleans. The branch table:

| `present` | `creating` | `finished` | `decoded` | Reading | Action |
|---|---|---|---|---|---|
| – | true | false | – | Gemini is still writing the answer | Still generating. Wait a jittered ~5s and probe again. Do not block on it, do not navigate. If I am also watching other rows, they get probed in the same sweep, not after row 3. |
| true | false | true | false | Finished on Gemini's clock, not yet decoded on ours | The probe just forced `eager` + `decode()`; `decode()` resolves before the next sweep. Re-probe once. Persisting past a couple of sweeps is a detection problem on our side, not generation latency — that is the distinction `finished` vs `decoded` exists to make. |
| true | – | – | true | Image is readable | Go to Step 4. |
| false | false | false | false | The tab shows neither an image nor the generating state | Not slow — empty. The send was dropped and the conversation opened blank. Give it the same short grace the script gives (75s from first sighting), then stop sweeping it and hand row 3 back for resubmission. Two such rows once ate an entire run's remaining budget. |
| (empty/unparsable bridge response) | | | | The bridge failed, not the page | Retry the probe once before treating it as the empty-tab case, since `evaluate` returns `""` on any bridge error and that is indistinguishable from a blank body. |

If the response is a `/sorry/` interstitial or the tab's URL has become
`google.com/sorry/index`, I stop, tell the user Google served its unusual-traffic
challenge, and let them clear it in the browser. I do not attempt the challenge.
Already-generated tabs are unaffected — only new navigations are, and I am making
none.

## Step 4 — Extract row 3's image (Branch C), in this order

All four calls carry `"session": "ppt-master-image-<slot + 1>"`. Nothing here
changes the tab.

1. **Note the clock** before clicking anything: the "new file since" test needs a
   `started` timestamp.
2. **Open the viewer** — `evaluate` with the script's `OPEN_VIEWER_JS`. There is no
   download button beside the inline result; the result `<img>` sits inside a
   `<button class="image-button">` and only the viewer renders `이미지 공유` /
   `이미지 복사` / `원본 크기 이미지 다운로드`. Every run that skipped this searched
   a tree that never had the button and silently fell back to the 1024px canvas
   copy.
   - returns `opened` → continue.
   - returns `no-image` / `no-button` → the viewer never opened. That is **row 3's
     problem alone**, not a browser setting: read the canvas copy for this row and
     leave the download path armed for every other row. Latching a global refusal
     here is the silent-degradation failure the rule exists to stop.
3. **Find the download control** — `snapshot`, then match
   `'role': 'button', 'name': '원본 크기 이미지 다운로드'`. The viewer animates in, so
   the action bar is not in the tree immediately: retry up to ~7 times with a
   jittered 0.35–0.8s gap. If the snapshot has no image *and* no download button at
   all, the answer is still rendering — that is the "keep polling" case, not a
   failure.
4. **Click it** by its `@eNN` ref, then **wait for the file**: poll
   `~/Downloads/Gemini_Generated_Image_*` for up to 25s for an entry newer than the
   `started` stamp. The original is a multi-megabyte PNG and takes 11–17s from click
   to file; a six-second wait once sent every row to the low-resolution fallback
   while reporting nothing wrong.
5. **Wait for the size to stop changing** — the file is still growing when it first
   appears. Compare `st_size` a second apart, up to ~8 times, and only treat it as
   complete when two consecutive reads match. One comparison a second apart once
   called a growing file a refusal.
6. **Copy it to `<out_dir>/<row-3-filename>`**, where `out_dir` is `--output` if the
   run used one, otherwise the manifest's folder. The filename comes from the
   manifest row, never from the download's own name.
7. **Clear every `Gemini_Generated_Image_*` newer than `started`**, on the success
   path and the failure path alike. One click can produce more than one file, and a
   click that timed out can still land its file a moment later; a leftover both
   fails the run's own "no leftovers" check and makes the next row read a stale file
   as its own.
8. **Close the viewer** — `snapshot`, match `'role': 'button', 'name': '닫기'`,
   click it. A viewer left open hides the next probe, and the tab must be left as it
   was found.

**Branch: the click produced no file at all.** That, and only that, is the browser
refusing the download. Then the canvas fallback (`CANVAS_JS` + the chunked
`window.__pptMasterGrab` readback) gives row 3 the displayed 1024px copy, and I
report to the user that `gemini.google.com` needs to be allowed under the browser's
automatic-downloads setting. I note explicitly that a *refusal* generalizes to the
rest of the run while a *viewer that never opened* does not.

## Step 5 — Verify before saying row 3 is done

- Row 3 reads `Generated` in the manifest and the file exists at
  `<out_dir>/<row-3-filename>`.
- Its ratio is within 4% of the row's `aspect_ratio`. The script prints
  `** ratio off, review this row` otherwise; that is a resubmit, not a footnote.
- Its long edge is not 1024px unless `--displayed-size` was asked for. The run
  prints a `**` line naming every row that fell back to the rendered copy; the
  absence of that line is the pass. Ratio and checksum both pass on a canvas copy,
  so resolution is the only check that catches a silent degradation.
- Its checksum differs from every other output file. An identical checksum means
  slot isolation broke — i.e. I read the wrong tab — and the run must be redone:

  ```bash
  shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
  ```

  This is the check that would catch an addressing mistake, so I run it even when
  only one row was read.
- `~/Downloads` holds no leftover `Gemini_Generated_Image_*`.

## Step 6 — Cleanup, only when the whole batch is finished

Four rows means four Chrome tab groups titled `agent:ppt-master-image-N` — one per
row, because merging sessions would mean merging tabs, which is the failure the
one-session-per-row design exists to prevent. Once every row reads `Generated` I
offer to clear them: `close_tab` on each slot session removes the tab and its group.
While any row is still `Pending`/`Failed`, the tabs stay — a `--collect-only` rerun
needs them.

Anything row 3 still refuses to give up stays `Pending` with its `last_error` set,
and I hand it back to the caller. The manifest is the record.
