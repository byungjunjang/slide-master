# S6 — The download control was clicked, the bridge said `ok`, no file arrived

Working directory for every command: the repo root
(`/Users/jaehyeonroh/Desktop/Personal/slide-master`). Manifest used throughout:
`projects/demo/images/image_prompts.json` — substitute the real project name.

The row in question is at slot `N`, i.e. bridge session `ppt-master-image-N+1`
(`slot_name(index)` = `ppt-master-image-<index+1>`).

---

## 0. What is already true, and what must not change

- The row's tab **already holds the finished image**. `export_to` is only ever
  called after `READY_JS` reported `decoded: true` (`naturalWidth > 300`), so the
  bytes are in the page and readable. Nothing about the failed download changed
  that.
- Therefore the recovery is a **read of the page**, not a regeneration.

Standing prohibitions for the rest of this scenario, each because breaking it is
a failure that already happened:

| Do not | Why |
|---|---|
| `navigate` the slot after submission | The tab already holds the finished image; re-opening the conversation is what makes it slow to decode or bounce to `/app` |
| Use `find_tab` | It returns `"ok": true` without switching tabs; a collection loop built on it wrote one image under four names |
| `close_tab` any slot | Not until every row reads `Generated`; a `--collect-only` rerun needs those tabs |
| Trust `{"ok": true}` | This bridge reports success for actions it did not perform — `find_tab`, `click`, and `navigate` all do. Verify the effect (the tab's URL, the file on disk), never the return value |

The `{"ok": true}` in this scenario is in fact **not consulted by the script at
all** — `export_to` throws away the click's return value
(`call("click", {"selector": found.group(1)}, session)` on its own line). The only
proof of a download the script accepts is a new
`~/Downloads/Gemini_Generated_Image_*`. So the correct reaction to "the bridge
said ok" is: ignore it, and go by the file.

---

## 1. Do not call it a refusal on a short wait

Before concluding anything, confirm the wait was the real one. The original is a
multi-megabyte PNG and takes 11–17s from click to file; a six-second wait once
sent every row to the low-resolution fallback while reporting nothing wrong.

What the script actually gives it:

- `DOWNLOAD_WAIT = 25` one-second polls for the file to *appear*
  (`newest_download(started)`, where `started` is stamped before the viewer is
  opened);
- then up to 8 more one-second polls for its **size to stop changing**, because a
  multi-megabyte PNG is still growing when it first appears and one comparison a
  second apart once called that a refusal.

**Decision point.** Did ~33s of polling elapse before "nothing appeared"?

- **Yes (the script ran the loop)** → proceed to step 2. This is the branch S6
  takes: the run is the script's, so the wait is by construction the full one.
- **No — I judged it by hand after a few seconds** → invalid. Do not latch, do
  not conclude. Let `export_to` finish its own loop and read its log line. A
  hand-timed check shorter than the script's is exactly the failure the 25s
  constant exists to prevent.

I do **not** race the script by polling `~/Downloads` myself while it runs:
`clear_downloads_since(started)` deletes everything newer than the click on both
paths, so my `ls` would either see a partial the script is about to remove or
nothing at all, and either reading would be noise. The log line is the record.

---

## 2. Classify the failure before latching — three causes, three branches

`export_to` distinguishes them and so must I. The evidence is the run's own log
line for this row:

| Log line | What happened | Scope |
|---|---|---|
| `original file via the viewer download (Ns)` | Worked | — |
| `the browser refused the download; reading the rendered image instead, and not attempting it again this run` | The control existed, was clicked, **no file** → `clicked = True`, `_download_refused = True` | **The whole rest of the run** |
| `viewer never opened (<opened>); reading the rendered image for this row only` | `OPEN_VIEWER_JS` returned `no-image` / `no-button` / empty, **or** it returned `opened` but `원본 크기 이미지 다운로드` never matched in 7 snapshots → `clicked` stayed `False` | **This row alone** |

**S6 is the middle row**: the download control was found and clicked. So the
branch I take is the latch — `_download_refused = True` for the remainder of the
process.

Why the distinction is load-bearing: latching on a viewer that failed to open
demoted every later row to 1024px over one bad moment, which is the same silent
degradation the rule exists to stop. A viewer that never opened is that row's
problem alone. Only a click that produced no file proves refusal. Conversely, a
browser that refuses one download refuses them all, so once refusal *is*
established, dropping the 25s wait for every later row is right, not lazy — it
buys back ~33s per row that would be spent proving the same thing again.

Note the third row's message is misleading when `OPEN_VIEWER_JS` returned
`opened` (the viewer did open; only its action bar never rendered). Read the
parenthesised value, not the sentence.

**Cost I accept by taking the latch:** every row collected after this one in this
same process also lands at 1024px. That is expected and is reported (step 4), not
a second failure to chase.

## 3. Get the image into the manifest's file — the canvas readback

This is the step that answers the scenario, and it is what `export_to` does next
automatically. No new command is needed; I let the run continue. The sequence,
in the slot's own session and nothing else:

1. `close_viewer(session)` — snapshot, match `'role': 'button', 'name': '닫기'`,
   click it. Leaves the tab as it was found so the next probe (and any later
   `--collect-only`) sees the page, not the overlay.
2. `clear_downloads_since(started)` — remove any partial the click landed late.
   Leaving it fails the run's own "no leftovers" check and makes the next row's
   newest-since test read a stale file as its own.
3. `evaluate(CANVAS_JS)` — find the first `blob:` `<img>` with
   `complete && naturalWidth > 300`, draw it into a canvas at
   `naturalWidth × naturalHeight`, stash `c.toDataURL('image/png')` on
   `window.__pptMasterGrab`, return `{len, w, h}`.
4. Pull the data URL back in `CHUNK = 600_000` slices via repeated
   `evaluate("(() => window.__pptMasterGrab.slice(o, o+CHUNK))()")` until
   `offset >= meta.len`.
5. `base64.b64decode` the payload after `data:image/png;base64,` and
   `dest.write_bytes(...)` to `projects/demo/images/<row filename>`.
6. `_canvas_rows.append(dest.name)` — the row is recorded as degraded.

Back in `collect`, the row then gets: ratio computed and compared against
`aspect_ratio` at `RATIO_TOLERANCE = 0.04`, `status = "Generated"`, `last_error`
and `slot` popped, and the manifest rewritten **immediately**. So the file is on
disk and the manifest reflects it even if the run is interrupted a second later.

Result: the image is in the manifest's file at the displayed size — 1024px on the
long edge instead of 2752px — with its aspect ratio intact.

**Decision point — the readback itself fails.** If `evaluate` returns empty, or
`CANVAS_JS` returns `{"error": "no decoded image"}`, `export_to` returns `()`.
Then `collect` sets
`last_error = "gemini-web: image could not be extracted yet"`, logs
`extraction failed, retrying next sweep`, and **keeps the row in the sweep**
rather than dropping it; the overall `--deadline` bounds the retries. Branch:

- **Retried and saved on a later sweep** → done, same as above.
- **Still failing every sweep** → the likely cause is the viewer still being open
  over the page (step 3.1 found no `닫기`, e.g. a non-Korean UI), so the probe and
  the canvas grab are looking at the overlay. Do not navigate to fix it. Let the
  deadline expire, leave the row `Pending`, and hand it back — a row this path
  cannot finish is the caller's, and the manifest is the record.
- **Deadline expires first** → `last_error = "gemini-web: still generating when
  the deadline expired"`, row stays `Pending`, tab stays open for a
  `--collect-only` rerun.

## 7. Optional second pass for the original — and its one blocker

The image is still sitting in its tab, undamaged, so once downloads are allowed
the original of *the same image* can be read out. That is strictly better than
regenerating, which would produce a different picture.

The blocker, stated plainly because it decides the branch: on a successful save
`collect` does `item.pop("slot", None)` and sets `status = "Generated"`. So the
saved row now has **no `slot`** — and `--collect-only` selects
`[(it["slot"], it) for it in batch if isinstance(it.get("slot"), int)]`, logging
`no recorded slot for … Resubmit them instead of collecting.` for the rest. §3
also says re-doing a `Generated` row means setting its status back to `Failed`
first; no flag does it.

- **Branch A — I wrote the slot number down at submit time** (§4 requires this,
  and the submit log plus the manifest as it stood at submit time are where it
  comes from). Then, in the manifest, set that row's `status` to `"Failed"` and
  restore **the recorded** `slot` integer. Then:

  ```bash
  python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
    --manifest projects/demo/images/image_prompts.json \
    --collect-only
  ```

  No `--displayed-size` (it would force the canvas copy again). `_download_refused`
  starts `False` in the fresh process, so the viewer download is retried; the tab
  was left closed-viewer and un-navigated, so the finished image is right there.
  Verify with step 5 that the long edge is now 2752/2048 and that the checksum
  differs from every other row.

- **Branch B — I do not have the recorded slot.** Do **not** reconstruct it.
  Slots are `enumerate` positions over the submitted batch, and re-numbering
  survivors points a row at another row's tab — row 3 alone becomes slot 1 and
  saves row 1's image under row 3's name. A row without a recorded slot is
  resubmitted, never guessed. So: set `status` to `"Failed"`, leave `slot` absent,
  and run a normal pass, accepting that Gemini generates a **new** image:

  ```bash
  python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
    --manifest projects/demo/images/image_prompts.json \
    --batch 1
  ```

  I tell the user the picture will change before running this.

Either branch, if the tab pile-up from the first run was already cleared, only
Branch B is possible — which is the reason step 0 forbids closing tabs early.

## 8. Cleanup, last

Only once every requested row reads `Generated` and step 5 passes: offer to clear
the tabs. Ten rows left ten Chrome groups titled `agent:ppt-master-image-N`,
one per session, because merging sessions would mean merging tabs — the very
thing the isolation exists to prevent. `close_tab` on each slot session removes
the tab and its group. I offer; I do not close anything while a row may still
need a `--collect-only` rerun.
