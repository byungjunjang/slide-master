# S3 — Execution plan: fill the manifest, WebBridge daemon refuses the connection

**Verdict up front:** this run does not start. `curl` to
`http://127.0.0.1:10086/command` returning nothing with connection refused is the
first row of the skill's precondition table failing, and §2 says: *"Stop and name
the failed precondition. Do not fall back to another image path from inside this
skill — that decision belongs to the caller."* Everything below is either the
diagnosis that makes that handback actionable, or the resume path if the user
brings the daemon up while I am still here.

"Proceed" means finish the diagnosis and report cleanly. It does not convert a
failed precondition into a passed one, and it is not authority to improvise a
different transport — the skill reserves the fallback decision for the caller.

---

## Step 0 — What the observed failure already tells me

| Fact | Consequence |
|---|---|
| Connection refused on `127.0.0.1:10086` | Nothing is listening on the port. This is the daemon being down, not the browser extension being disconnected and not a signed-out Gemini session. |
| Empty response body | `call()` gets empty stdout, `json.loads` raises `JSONDecodeError`, and it returns `{"ok": False, "error": {"message": ""}}` — an **empty** message. So the script's own log would not distinguish "port closed" from "extension disconnected"; the curl exit status is the discriminator, and I have it. |
| `require_daemon()` runs before anything else in `main()` | It precedes the manifest read, the output-dir resolution, and every `navigate`. A run attempted now aborts with `RuntimeError: Kimi WebBridge is not answering on 127.0.0.1:10086…` having touched no file and opened no tab. |

**Decision — do I run the script anyway to "confirm"?** No. It is side-effect free
(it dies at `require_daemon()` before reading the manifest), so running it would
be harmless, but it returns strictly less information than the curl result I
already hold: the same conclusion with an empty error message attached. I skip
it and report from the evidence in hand.

**Decision — do I retry the curl?** One retry at most, and only if I have reason
to think the daemon is mid-restart. Connection refused is a hard, immediate
failure with no timeout involved; repeating it is not a diagnostic. I do not
loop on it.

## Step 2 — Local checks that need no bridge (read-only, safe while the daemon is down)

These cost nothing, cannot touch the browser, and make the handback specific
instead of "it broke". They do not constitute proceeding with the run.

```bash
# Row inventory: what this run would have taken, and what is off-limits.
python3 - <<'PY'
import json, pathlib
p = pathlib.Path("projects/<name>/images/image_prompts.json")
m = json.loads(p.read_text(encoding="utf-8"))
rows = m["items"]
for label in ("Pending", "Failed", "Generated", "Needs-Manual"):
    print(label, sum(1 for r in rows if r["status"] == label))
print("with a recorded slot:",
      [r["filename"] for r in rows if isinstance(r.get("slot"), int)])
print("aspect ratios pending:",
      sorted({r["aspect_ratio"] for r in rows if r["status"] in {"Pending", "Failed"}}))
PY
```

What each outcome changes:

- **Zero `Pending`/`Failed` rows** → the daemon being down is moot; the script
  would print *"nothing to do — every row is already Generated"* and return.
  I say so and stop, without asking the user to start anything. (§3: re-doing a
  `Generated` row means setting it back to `Failed` first; no flag does it.)
- **`Needs-Manual` rows present** → I name them as never-submitted-by-design.
  `RETRYABLE = {"Pending", "Failed"}` excludes them deliberately; selecting on
  "not Generated" would have sent the user's hand-supplied figures to Gemini as
  prompts.
- **Rows already carrying `slot`** → leftovers from an earlier run. They do not
  survive this outage: the tabs those numbers referred to belong to a browser
  session the dead daemon can no longer address, so `--collect-only` is **not**
  the resume path (Step 5). A fresh submission overwrites `slot` anyway.
- **`pending > 10`** → the resume run takes only the first 10 (`--batch` default)
  and logs *"N rows pending; taking 10 this pass"*. I state the number of passes
  up front so it is not a surprise.

```bash
# §5.5 pre-state: leftovers here would fail the run's own end-of-run check.
ls -l ~/Downloads/Gemini_Generated_Image_* 2>/dev/null
```

- **Leftovers found** → I report them and ask the user before removing anything.
  `clear_downloads_since()` only deletes files newer than the click that produced
  them, so a pre-existing file survives the whole run and then fails §5.5 while
  looking like this run's fault. Deleting a user's downloaded files is not mine
  to do unasked.
- **Nothing found** → clean baseline; note it and move on.

I write **nothing** to the manifest at this stage. The script never reached its
first `write_text`, the rows are already in the status they should be in, and
inventing a `last_error` by hand is not in the contract (§7: rows this skill
cannot finish stay `Pending`; the manifest is the record).

## Step 5 — Resume path, if the daemon comes up in this session

**Re-gate first.** Re-check the daemon before anything else — a single
`list_tabs` returning `"ok": true`, which is what `require_daemon()` does itself.
If it still refuses, I stop again; I do not start a run hoping the port opens
mid-flight.

**Submission run, not collection.** `--collect-only` reads `it["slot"]` and needs
tabs that are still open. Nothing was ever submitted through this outage, so
either the rows carry no `slot` (the script logs *"no recorded slot for … so
their tabs cannot be identified. Resubmit them instead of collecting."* and, with
no usable slots, prints *"nothing to collect"* and returns) or they carry a stale
`slot` pointing at tabs from a dead session — the worse outcome, since §4 warns
that a mis-numbered slot saves one row's image under another row's name. First
run after the outage is always a fresh submission.

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

Flag decisions:

- **`--manifest`** — required, the project's `images/image_prompts.json`.
- **`--output` omitted** — images belong beside the manifest, which is the
  contract Step 6 of ppt-master reads.
- **`--batch` left at 10** — §3: generate the whole set in one pass; concurrency
  shows no per-image penalty, so splitting only repeats the ~48s submission cost.
  Lowered *only* if a run hits the unusual-traffic challenge.
- **`--generate-wait` left at 10** — a single image was ready ~28s after submit;
  early sweeping costs one cheap probe per slot.
- **`--displayed-size` off** — I want originals (2752x1536 for 16:9), and §5.4
  makes 1024px a failure unless it was asked for. I turn it on only if the user
  says the deadline matters more than the pixels.
- **`--deadline`** — default 300 for a small set (2 rows measured 81s). For a
  ten-row set at original size, §5.1 puts ~220s of unavoidable serial work
  (~10s submit + ~12s download per row) against a 300s budget and calls that
  "near the deadline, not comfortably inside it" — the one measured originals run
  took 424s and finished 8/10. So for ~8–10 originals I raise it up front:
  `--deadline 480`. That number is my extrapolation from §5.1's serial cost plus
  20–50s of generation and margin — it is not a figure the skill measured. §7
  sanctions raising the deadline; it forbids lowering `--batch` on this evidence.

**Say the tab cost once, at submit time** (§3): ten rows leave ten Chrome tab
groups titled `agent:ppt-master-image-N`, one per row, because merging sessions
would merge the tabs and destroy the isolation §1 rests on. Offer to clear them
with `close_tab` per slot session **after** every row reads `Generated` — a
`--collect-only` rerun needs those tabs.

**What I watch in the log, and where each outcome goes:**

| Log signal | Branch |
|---|---|
| `prompt box never appeared` on **every** row | Read the tab's URL before blaming the UI language (§7). `google.com/sorry/index` = Google's unusual-traffic challenge: stop, tell the user, let a person clear it in the browser — do not attempt the challenge, and note that already-generated tabs are unaffected. Otherwise it is a signed-out session or a non-Korean UI, which look identical from the log. |
| `send did not take … retrying once` / `send never took` | The script's own handling: a conversation URL is not proof the prompt was sent, so it re-fills and resends once, then leaves the row `Pending`. I resubmit such rows in a later pass; I never count them. |
| `no answer started — dropping it` | A blank tab, not a slow one. The script clears its `slot` so a later `--collect-only` is not pointed at it. That row needs resubmission. |
| `sweep N: K still generating` | Normal. Slots are swept concurrently and no slot blocks another; I do not intervene. |
| `viewer never opened (…)` | That row alone fell to the 1024px canvas copy; the next row still gets its shot at the original. Re-run that row with `--collect-only` — its tab is still open and usually yields the original. |
| `the browser refused the download` | The click produced no file, so the wait is dropped for the whole run. Check the browser's automatic-downloads setting for `gemini.google.com`, then re-run the affected rows. |
| `** ratio off, review this row` | Resubmit that row. §5.2: it is a resubmit, not a footnote. |
| `** K of N row(s) fell back to the 1024px rendered copy` | §5.4 failure unless `--displayed-size` was asked for. Named rows get re-run. |
| Deadline expires with rows unsaved | §7: re-run with `--collect-only` (tabs still hold their images; nothing is regenerated) or raise `--deadline`. Do **not** lower `--batch` on this evidence — the measurement that seemed to show concurrent generations slowing each other came from the broken readiness probe. |

**Verification before I claim success (§5), all five:**

1. Every requested row reads `Generated` and its file exists on disk.
2. Each file's ratio is within 4% of its row's `aspect_ratio` — no `** ratio off`
   line.
3. No two output files share a checksum; identical files mean slot isolation
   broke and the run is redone, not patched:
   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
4. No file is 1024px on its long edge unless `--displayed-size` was requested —
   the absence of the `**` fallback line is the pass. Ratio and checksum both
   pass on a canvas copy, so resolution is the only check that catches a silent
   degradation.
5. `~/Downloads` holds no leftover `Gemini_Generated_Image_*`.

Rows that still cannot be finished stay `Pending` and go back to the caller with
their `last_error`. The manifest is the record.
