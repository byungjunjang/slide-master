## Step 0 — Preconditions (§2), before anything is typed

Checked in this order; on any failure I **stop and name the failed
precondition**, and I do **not** fall back to another image path — that decision
belongs to the caller.

1. **Daemon.** `list_tabs` must answer `"ok": true`. `require_daemon()` does this
   for me on any invocation of the script, so I do not pre-poke the daemon by
   hand; if the script raises `Kimi WebBridge is not answering on
   127.0.0.1:10086`, that is the failed precondition and the run stops there.
2. **Gemini signed in** — the account chip renders on `gemini.google.com`. A
   signed-out page has no prompt box and is indistinguishable in the log from a
   non-Korean UI, so if submissions later fail I read the tab's URL rather than
   guessing (§7).
3. **Browser UI is Korean.** The script matches five accessible names
   (`Gemini 프롬프트 입력`, `메시지 보내기`, `사용해 보기`,
   `원본 크기 이미지 다운로드`, `닫기`). Another UI language needs all five
   re-read from a live page first; I do not guess them.
4. **Manifest is valid** and holds `Pending`/`Failed` `ai` rows:

   ```bash
   python3 -c "
   import json
   m = json.load(open('projects/<name>/images/image_prompts.json'))
   for i in m['items']:
       print(i['status'], i.get('slot'), i['aspect_ratio'], i['filename'])
   "
   ```

   Confirms three retryable rows, and that no `Needs-Manual` row is in scope
   (those belong to the user and are never submitted).
5. **Automatic downloads** for `gemini.google.com` — optional. Without it the run
   still finishes at the displayed size, and the run says so itself with a `**`
   line.

**Told to the user once, at submit time:** three rows means three bridge
sessions, so three Chrome tab groups appear — `agent:ppt-master-image-1`,
`-2`, `-3`. That is the cost of slot isolation, not a bug; sessions cannot be
merged without merging the tabs, which is exactly the failure the one-session-
per-row design prevents. I offer to clear the groups when the run is fully
resolved, not before.

## Step 1 — The run

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

**Flag decisions:**

- No `--batch`: three rows are under the default 10, and the whole set goes in
  one pass. Splitting would only repeat the submission cost.
- No `--deadline`: at the measured ~10s serial submit per row and ~12s serial
  download per row, three originals are roughly 66s of unavoidable serial work
  plus generation that typically lands 20–50s after submit. The 300s default has
  wide margin for three rows; it is ten-row decks of originals that sit near the
  edge.
- No `--displayed-size`: the deadline is not the binding constraint here, and
  §5's resolution check exists precisely so a run does not quietly ship 1024px
  copies. I want the originals.
- No `--collect-only` on this first invocation: nothing has been submitted yet.
- No `--output`: images land beside the manifest.

The script writes each row's `slot` into the manifest as it submits, and writes
the manifest again after the submission loop. I never compute or hand-edit a
slot number — `--collect-only` runs in a fresh process, and by then some rows are
`Generated`, so re-numbering the survivors would point a row at another row's
tab.

---

## Step 2 — What I read out of the collection log

The script settles `--generate-wait` (10s) and then sweeps every slot
concurrently, ~5s jittered between sweeps, never blocking on one slot. I do not
interrupt it, and I do not touch the browser while it runs:

- **No navigation, no reload of any slot.** The tab already holds the finished
  image; re-opening a conversation is what makes it decode slowly or bounce to
  `/app`.
- **No `find_tab`, ever.** It returns `"ok": true` without switching tabs; a
  collection loop built on it once wrote one image under four file names. The
  session name *is* the handle on the tab.
- **No killing the process to "fix" the stuck row.** Each saved file is written
  back to the manifest immediately, so nothing is lost by letting it run, and
  every remaining sweep is another chance for the stuck row to decode.

Expected lines: two `saved <filename> WxH ratio ... [sweep N, read at Ns, gemini
done at Ms, lag Ls]` lines, and `sweep N: 1 still generating` repeating for the
third.

**Decision point A — does the stuck row recover on its own?** The readiness
probe already applies the only fix the skill documents for `naturalWidth` 0: it
sets `img.loading = 'eager'`, scrolls the element to centre, and calls
`img.decode()` on every sweep, because the result is laid out at zero size and
`scrollIntoView` on a zero-box element is a no-op. There is nothing I can do by
hand that the sweep is not already doing every few seconds.

- If a `saved` line appears for the third row before the deadline → the fix
  landed late; the run ends 3/3 and I go straight to Step 5 (verification).
- If it never appears → the run reaches the deadline. Expected tail:
  `... : not ready before the deadline — left Pending`, then
  `saved 2 this run · manifest 2/N · ~300s elapsed (OVER the 300s deadline)`.

**What the stuck row will *not* do:** it will not be dropped as a dead row. The
dead-row grace fires only when a tab shows neither an image nor "Creating your
image"; here an image element is present, so the slot counts as alive and keeps
its recorded `slot` key in the manifest all the way to the deadline. That is what
makes Step 4 possible.

## Step 3 — Diagnose the stuck row, read-only, after the process exits

I wait for the process to exit before probing, for two reasons: an extra
`evaluate` against the same session contends with the sweep, and the answer
cannot change my action mid-run anyway — I have no legal intervention while the
script is sweeping.

First, read the recorded slot rather than assuming it:

```bash
python3 -c "
import json
m = json.load(open('projects/<name>/images/image_prompts.json'))
for i in m['items']:
    print(i['status'], repr(i.get('slot')), i['filename'], i.get('last_error',''))
"
```

The session for the surviving row is `ppt-master-image-<slot+1>` — for the third
submitted row, slot `2` → session `ppt-master-image-3`. If the row has no
integer `slot`, it cannot be collected at all and must be resubmitted (Branch 3).

Then one read-only probe, sent as a **file body** (an inlined JSON body loses
non-ASCII text and breaks on quoting), with no click and no navigation in it:

```bash
cat > "$SCRATCH/probe.json" <<'JSON'
{"action":"evaluate","session":"ppt-master-image-3","args":{"code":"(() => { const imgs = [...document.querySelectorAll('img')].filter(i => i.src.startsWith('blob:')); return JSON.stringify({ url: location.href, creating: document.body.innerText.includes('Creating your image'), tail: document.body.innerText.slice(-160), n: imgs.length, imgs: imgs.map(i => { const r = i.getBoundingClientRect(); return {nw: i.naturalWidth, nh: i.naturalHeight, complete: i.complete, loading: i.loading, box: [Math.round(r.width), Math.round(r.height)], inButton: !!i.closest('button'), btnClass: i.closest('button') ? i.closest('button').className : null}; }) }); })()"}}
JSON
curl -s -m 120 -X POST http://127.0.0.1:10086/command \
  -H 'Content-Type: application/json' \
  --data-binary "@$SCRATCH/probe.json"
```

I read the tab's own `url` in that result — never the bridge's return value — as
my proof of which page I am looking at. This bridge reports success for actions
it did not perform.

Three things the probe settles, and where each leads:

| Probe reading | Reading means | Branch |
|---|---|---|
| `creating: true` (page tail still ends in "Creating your image") | Gemini is genuinely still rendering. Not a detection bug | **Branch 1** |
| `creating: false`, exactly one blob img, `inButton: true`, `nw: 0`, `box` at or near `[0,0]` | The answer finished; the zero-box lazy decode never fired despite the eager+decode fix | **Branch 2** |
| `n > 1`, or the matched img is not inside a `button` | The probe's "first blob img" is latching onto something that is not the result element, so the readiness test can never pass on this tab | **Branch 3** |
| `url` is `https://www.google.com/sorry/index?...` | Google's unusual-traffic challenge | **Branch 4** |

## Step 4 — Branches

### Branch 1 — still generating

The tab holds a live generation; nothing is wrong and nothing needs
regenerating. Re-sweep the tab that is already open, in a fresh process, with a
raised budget:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --collect-only --deadline 420
```

`--collect-only` reads the recorded `slot` and drives session
`ppt-master-image-3` only; the two `Generated` rows are not retryable, so they
are not selected and their tabs are not read. The whole 420s goes to sweeping one
slot, since there is no submission cost in a collect-only pass.

If it saves → Step 5. If this pass, too, ends at the deadline with the same
state, I stop treating it as slow and move to Branch 3.

### Branch 2 — finished, but the decode never fires

One `--collect-only` pass, fresh process, same tab, default budget:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --collect-only
```

Why this is worth exactly one attempt and not more: a new process re-issues the
`loading = 'eager'` + `decode()` fix against a page that has now been idle, which
is the documented remedy and the same thing that turns a "viewer never opened"
row into an original on a rerun. It is the only lever the skill defines for this
symptom.

I do **not** try to hand-extract the image while it reads zero. Both extraction
paths are gated behind a decoded element — the canvas readback itself requires
`naturalWidth > 300`, and the viewer download is only reached for a row the sweep
has already marked ready — so there is no manual shortcut here, only a way to
save a broken file. If this pass also ends at the deadline → Branch 3.

### Branch 3 — resubmit the row (last attempt)

The row is `Pending`, the other two are `Generated` and therefore not retryable,
so a normal run takes exactly this one row:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

What this does and why it is safe: `submit()` opens a **new** tab in session
`ppt-master-image-1` (the row is index 0 of a one-row batch) and overwrites the
row's `slot` to `0`. Row 1's original tab is abandoned, which costs nothing —
its image is already saved and its manifest row is `Generated`. Nothing about
this re-navigates a slot that is still owed an image; the only tab still owed an
image is `ppt-master-image-3`, and I leave it untouched rather than reloading it.

I watch for `submitted <filename>` — the script requires the answer to have
*started*, not merely a conversation URL, and resends once on its own if it has
not.

Retry budget stops here. If this attempt also fails, the row stays `Pending`
with its `last_error` and is handed back to the caller; the manifest is the
record.

### Branch 4 — `/sorry/` interstitial

If the probe's `url`, or a resubmission's `prompt box never appeared` failure,
points at `https://www.google.com/sorry/index?continue=…`, I **stop
immediately**. I do not attempt the challenge and I do not retry submissions —
there is no prompt box on that page, so every later submission fails the same
way. I tell the user that Google served its unusual-traffic challenge and that
only a person can clear it in the browser. Already-generated tabs are
unaffected; the two saved rows stand, and only new navigations are blocked. When
the run resumes afterwards, I lower `--batch` — that is the one symptom the flag
exists for.

## Step 5 — Verify before reporting success (§5)

Run on whatever the run produced, whether that is 2/3 or 3/3.

1. **Status and file existence** for every row I claim:

   ```bash
   python3 -c "
   import json, os
   m = json.load(open('projects/<name>/images/image_prompts.json'))
   for i in m['items']:
       p = os.path.join('projects/<name>/images', i['filename'])
       print(i['status'], os.path.exists(p), os.path.getsize(p) if os.path.exists(p) else 0, i['filename'])
   "
   ```

2. **Ratio within 4%** — the run prints `** ratio off, review this row` for any
   miss. That row needs a resubmit (Branch 3), not a footnote in the report.

3. **No two files share a checksum.** Identical files mean slot isolation broke
   and the whole run has to be redone:

   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```

4. **No file is 1024px on its long edge** — `--displayed-size` was not asked
   for. The absence of the `** N of M row(s) fell back to the 1024px rendered
   copy` line is the pass; I confirm it against the pixels too, since ratio and
   checksum both pass happily on a canvas copy and resolution is the only check
   that catches a silently degraded run:

   ```bash
   python3 -c "
   import glob
   for p in sorted(glob.glob('projects/<name>/images/*.png')):
       raw = open(p,'rb').read(24)
       print(p, int.from_bytes(raw[16:20],'big'), int.from_bytes(raw[20:24],'big'))
   "
   ```

   16:9 originals read 2752x1536 and 1:1 reads 2048x2048. If the `**` line says
   `the browser refused the download`, the click produced no file and the run
   stopped trying for every later row — I check the browser's automatic-downloads
   setting for `gemini.google.com` before rerunning. If it says
   `viewer never opened`, that is one row's bad luck and a `--collect-only`
   rerun usually gets it the original.

5. **No leftovers in `~/Downloads`:**

   ```bash
   ls -la ~/Downloads/Gemini_Generated_Image_* 2>/dev/null || echo "no leftovers"
   ```

   A partial left behind both fails this check and poisons the next row's
   newest-since test.

## Step 6 — Tabs

I do **not** close any tab until every row is either `Generated` or finally
handed back — a `--collect-only` rerun needs those tabs, and the stuck row's tab
is the only place its image exists. Once the run is resolved I offer the cleanup,
and only on the user's yes:

```bash
for n in 1 2 3; do
  cat > "$SCRATCH/close-$n.json" <<JSON
{"action":"close_tab","session":"ppt-master-image-$n","args":{}}
JSON
  curl -s -m 120 -X POST http://127.0.0.1:10086/command \
    -H 'Content-Type: application/json' --data-binary "@$SCRATCH/close-$n.json"
done
```

Closing a slot session removes its tab and its `agent:ppt-master-image-N` group.
I confirm with `list_tabs` rather than trusting the returns.

- **No fallback to another image path.** Choosing a different backend is the
  caller's decision, not this skill's.

## Things I deliberately do not do in this scenario

- Use `find_tab` to locate the stuck tab. The session is the handle.
- Navigate, reload, or re-open the conversation in slot 3 — that is what makes a
  finished image decode slowly or bounce to `/app`.
- Block on the stuck slot while the other two are outstanding; the sweep is
  round-robin by design, and blocking is what once reported two finished images
  as failures with the files sitting ready in their tabs.
- Re-number slots by hand, or run `--collect-only` against a row with no
  recorded `slot`.
- Close tabs before every row is resolved.
- Hand-roll a canvas or viewer extraction on a zero-decode element — both paths
  require a decoded image, so the only thing available is a corrupt file.
- Answer the unusual-traffic challenge.
- Add `--displayed-size` to "make it fit"; the deadline is not what is failing.
- Lower `--batch` on this evidence. Three concurrent rows is not the problem —
  the one measurement that appeared to show concurrent generations slowing each
  other down came from the broken readiness probe, and that superseded 10m29s
  run is not quoted.
