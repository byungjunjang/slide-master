### 1.2 Decision point — a stale `slot` on a `Failed` row

This is the one trap specific to S2. `--collect-only` reads `it["slot"]` and
sweeps that tab. A stale slot from a dead attempt points at a tab whose contents
I cannot attribute, and the skill's own worked example of this failure is a row
saving *another row's* image under its name.

The slot on a `Failed` row is untrustworthy on its face: **this script never
writes the status `Failed`** — it leaves unfinished rows with a `last_error` and
their incoming status. So a `Failed` + `slot` pair was not produced by a
completed submit from this script, and the tab it names may have been closed,
reused, or never held that row at all.

- **Default branch (what I take unless the check below passes cleanly): strip
  the stale slots and submit fresh.**

```bash
python3 - <<'PY'
import json
from pathlib import Path
p = Path("/Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/image_prompts.json")
m = json.loads(p.read_text(encoding="utf-8"))
dropped = [it["filename"] for it in m["items"]
           if it["status"] == "Failed" and it.pop("slot", None) is not None]
p.write_text(json.dumps(m, ensure_ascii=False, indent=2) + "\n", encoding="utf-8")
print("cleared stale slot on:", dropped or "none")
PY
```

  Rationale: a row without a slot is resubmitted, never guessed — that is the
  rule. Stripping makes the "never guessed" path the only one available. It also
  closes a real gap: if a row's submit fails later in this run, its `slot` is
  never set, but a *stale* one would have survived the write-back at the end of
  the submit loop and misdirected a future `--collect-only`.

- **Alternative branch (only if all of these hold): keep the slots and open with
  `--collect-only`.** All four rows carry an int `slot`; the user confirms the
  earlier attempt was this same script against this same manifest and its tabs
  were never closed; and `list_tabs` on `ppt-master-image-1..4` shows each
  session still holding a `gemini.google.com/app/<id>` tab. That recovers
  finished images for free. If even one of the three fails, I take the default
  branch. I never use `find_tab` to establish this — it returns `"ok": true`
  without switching tabs, and a collection loop built on it wrote one image under
  four different names.

## 2. Preconditions (§2 of the skill) — stop and name the one that fails

1. **WebBridge daemon.** `list_tabs` on session `ppt-master-image` returns
   `"ok": true`. The script enforces this itself via `require_daemon()`; if it
   raises, the message is the answer — start the daemon, confirm the extension
   is connected, rerun. Do not proceed past this.
2. **Gemini signed in + UI language + no standing challenge.** One cheap probe
   on the shared prefix session (`ppt-master-image`, the same session
   `require_daemon` uses) — navigate it to `https://gemini.google.com/images`,
   snapshot, and look for the textbox named `Gemini 프롬프트 입력`. I use the
   prefix session, never `ppt-master-image-1..4`: those are slot sessions and a
   slot must not be navigated for anything but its own submission.
   - Textbox present → signed in, UI is Korean, proceed.
   - `사용해 보기` present → first-visit onboarding; the script dismisses it, so
     this is not a blocker.
   - No prompt box → **read the tab's URL before blaming anything.**
     `https://www.google.com/sorry/index?continue=…` means Google's
     unusual-traffic interstitial. I do not attempt it — no CAPTCHA, no
     challenge answering. Stop, tell the user, wait for them to clear it in
     their browser. Any other URL with no prompt box means signed out or a
     non-Korean UI; these look identical in the log, which is exactly why I read
     the URL. Stop and name which.
   - Non-Korean UI → stop. All five accessible names (`Gemini 프롬프트 입력`,
     `메시지 보내기`, `사용해 보기`, `원본 크기 이미지 다운로드`, `닫기`) would
     have to be re-read from a live page first. I do not guess translations.
3. **Downloads land silently (optional).** `gemini.google.com` allowed under the
   browser's automatic-downloads setting gives originals; without it the canvas
   fallback still completes the run at 1024px. Not a blocker, but it decides
   which §5 check is likely to fire.
4. **Manifest** — done in §1.

I do **not** fall back to another image path from inside this skill if a
precondition fails. That decision belongs to the caller.

## 5. Reading the log live — every line I watch and the branch it triggers

Expected shape: `submitting 4 prompt(s), one tab each` → four `submitted <file>
(<ratio>)` lines → `4 submitted in ~45s; settling 10s before the first sweep` →
`sweep N: M still generating` → `saved …` lines → the summary line.

| What the log says | What it means | Branch |
|---|---|---|
| `submitted <file> (16:9)` ×4 | Send verified: the tab left `/images` for a conversation URL **and** the answer had started. A conversation URL alone is not proof, and the script checks both. | Proceed. |
| `send did not take …; retrying once` then `submitted` | One dropped send, recovered. | Proceed. |
| `send never took … — leaving it Pending` | The row has **no** `slot` recorded. | Do not try to collect it later; it must be resubmitted in a second pass (§6b). |
| `prompt box never appeared` on **one** row | Transient page load or a lost tab. | Let the run continue; resubmit that row afterwards. |
| `prompt box never appeared` on **every** row | Check the tab URL, not the UI language first. | `google.com/sorry/index` → stop the run, tell the user, do not answer the challenge; already-generating tabs are unaffected, only new navigations. Otherwise → signed out, or a non-Korean UI: stop and name it. |
| `navigate failed twice for <file>` | Bridge could not open the tab even after its one retry. | Row is skipped, no slot; resubmit later. |
| `sweep N: M still generating` | Normal. Sweeps are concurrent across slots and jittered around 5s, so a slow row never blocks the others. | Wait. I never block on a single row or watch one tab in place. |
| `saved <file> 2752x1536 ratio 1.792 … [sweep k, read at Xs, gemini done at Ys, lag Zs]` | Original landed. `finished` vs `decoded` split tells me whether any delay was Gemini's or ours. | Proceed. Status is already written back to the manifest for that row immediately. |
| `original file via the viewer download (13s)` | The viewer was opened, `원본 크기 이미지 다운로드` was clicked, the file arrived and stopped growing. | Proceed. |
| `viewer never opened (no-image\|no-button\|opened)` | **That row alone** fell to the 1024px canvas copy. The run correctly does not latch on this. | Do not treat it as a browser-wide refusal. Re-run that row with `--collect-only` afterwards (§6a) to get the original. |
| `the browser refused the download; … not attempting it again this run` | A control that was present was clicked and no file appeared. Every later row goes canvas. | Let the run finish (the images are still real), then check Chrome's automatic-downloads setting for `gemini.google.com`. To redo those rows at full resolution afterwards: set their status back to `Generated`→`Failed` by hand and re-run — no flag does it. |
| `<file>: no answer started — dropping it` (after the 75s grace) | The tab is blank, not slow: the send was dropped. Its `slot` is removed so a later `--collect-only` is not pointed at a blank tab. | Resubmit that row (§6b). This drop is what stops one dead row from eating the whole budget. |
| `<file>: extraction failed, retrying next sweep` | Kept in the sweep on purpose; the deadline bounds the retries. | Wait. |
| `<file>: not ready before the deadline — left Pending` | Deadline expired. Note: the row keeps its incoming status (`Failed` here) with `last_error` set. | §6a — its tab is still open and still holds the image; `--collect-only` recovers it without regenerating. Do **not** lower `--batch` on this evidence. |
| `** ratio off, review this row` | Drift > 4% from the row's `aspect_ratio`. | That row needs a resubmit, not a footnote. |
| `** N of M row(s) fell back to the 1024px rendered copy … : <names>` | Silent degradation, now loud. | §6a for those rows. |
| final `saved 4 this run · manifest 6/6 · 175s elapsed (within the 300s deadline)` | Target state. The `6/6` includes the 2 pre-existing `Generated` rows. | Go to §7. |
| `finished inside the deadline with N row(s) unsaved — re-run with --collect-only` | The script telling me which follow-up to run. | §6a. |

Throughout: **I never navigate, reload, or otherwise touch a slot tab after its
submission**, and I never use `find_tab`. This bridge reports success for actions
it did not perform — I verify the effect (a file on disk, a tab's URL), never a

## 6. Second pass, if the run does not come back 6/6

**(a) Rows with a recorded `slot` that did not save** — deadline expiry,
extraction failure, or a 1024px fallback I want to redo at full size. Their tabs
are still open and hold the finished image; nothing needs regenerating.

```bash
cd /Users/jaehyeonroh/Desktop/Personal/slide-master && \
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json --collect-only
```

Why this is safe *now* and was not in §1.2: by this point the slots were written
down by this run's own successful submissions, and rows that saved are
`Generated` and drop out of the batch, while the survivors carry their own
`slot`. That is exactly the re-numbering hazard the recorded slot exists to
prevent — row 3 alone must not become slot 1 and save row 1's image under row
3's name. If the run logs `no recorded slot for <files>`, those rows go to (b),
not here.

If the deadline was the problem and the sweep needs more room, add
`--deadline 480` to the same command rather than reaching for `--batch`.

**(b) Rows with no `slot`** — send never took, navigate failed, or the row was
dropped as dead. Resubmit them: same command as §4, no `--collect-only`. They
are still `Failed`, so they are picked up automatically; slot numbers for this
smaller batch are assigned fresh at submit time and written back, so the mapping
stays honest.

**(c) Unusual-traffic challenge appeared.** Stop. Tell the user; only a person
can clear it. On resume, re-run §4 with `--batch 2` and accept two passes.

Rows this skill cannot finish are handed back to the caller with the manifest as
the record. I do not silently mark anything `Generated`.
