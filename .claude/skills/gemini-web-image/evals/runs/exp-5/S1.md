# S1 — Execution plan: fill `projects/demo/images/image_prompts.json` (4 Pending rows, 2×16:9 + 2×4:3)

Everything below is derived only from `SKILL.md` and `scripts/gemini_web_image.py`.
One bridge session per row; the script owns submission, sweeping, download and
manifest write-back. I drive nothing in the slot tabs myself.

## Step 1 — The run (single command, all defaults)

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/demo/images/image_prompts.json
```

Every flag decision, stated:

| Flag | Value | Why |
|---|---|---|
| `--manifest` | `projects/demo/images/image_prompts.json` | Required. |
| `--output` / `-o` | **omitted** | Default is the manifest's folder, `projects/demo/images/`, which is exactly where the ppt-master contract wants `images/<filename>`. Passing it adds a way to be wrong. |
| `--batch` | **omitted (10)** | 4 pending ≤ 10, so all four go in one pass and the `"N rows pending; taking M this pass"` line will not appear. §3: generate the whole set in one pass — concurrency shows no per-image penalty, and splitting only repeats the serial submission cost. The single reason to lower it is Google's unusual-traffic challenge, and none has been seen; §7 forbids lowering it on deadline evidence alone. |
| `--generate-wait` | **omitted (10)** | A row is typically ready 20–50s after submit; a longer pre-wait is dead time and sweeping early costs one cheap probe per slot. |
| `--deadline` | **omitted (300)** | Budget for four rows: ~10s serial submit per row (2 rows measured 21s) ≈ 40s, generation 20–50s largely overlapping, ~12s serial download per row ≈ 48s, plus the 10s settle → roughly 100–150s. The measured 2-row original-size run was 81s. 300s has real margin here; the 10-row squeeze in §5.1 does not apply to 4 rows. |
| `--displayed-size` | **omitted** | Originals wanted (2752×1536 for 16:9, 2400×1792 for 4:3). It only buys back ~12s per row, and the deadline is not the binding constraint at four rows. Setting it would also flip `_download_refused = True` up front and suppress the `**` fallback report. |
| `--collect-only` | **omitted** | Nothing has been submitted yet; the rows carry no `slot`. |

I do **not** touch the slot tabs while the script runs: never `find_tab` (it
returns `"ok": true` without switching and once wrote one image under four
names), never `navigate` a slot after submitting (the tab already holds the
finished image), never press Enter instead of the send button.

## Step 2 — Read the log as it runs; record the slot mapping

Expected shape:

```
submitting 4 prompt(s), one tab each
  submitted <a>.png (16:9)
  submitted <b>.png (4:3)
  ...
4 submitted in ~40s; settling 10s before the first sweep
  sweep 1: 4 still generating
  saved <a>.png 2752x1536 ratio 1.792 vs 16:9 (… bytes) [sweep n, read at …s, gemini done at …s, lag …s]
    original file via the viewer download (…s)
  ...
saved 4 this run · manifest 4/4 · …s elapsed (within the 300s deadline)
```

**Write the slot numbers down** from the submit order (§4). Submission order is
manifest order among the retryable rows, so row *k* (0-based) gets `slot: k` in
the manifest and session `ppt-master-image-{k+1}` — the manifest value is
0-based, the session/tab-group name is 1-based. I note the filename→slot pair
myself as well, because the script **removes** `slot` from a row the moment it
saves it (`item.pop("slot")`), and any later `--collect-only` recovery for that
row needs the number back.

### Decision points during the run

| What the log/page says | What I check | Branch taken |
|---|---|---|
| `navigate failed twice for <f>` | Nothing further — the script already retried once | That row is skipped and stays `Pending`; handle it in Step 4 with a plain re-run (it has no `slot`). |
| `prompt box never appeared for <f>` (one or all rows) | **Read the tab's URL before blaming the UI language** (§7): `evaluate` `location.href` on that slot's session — read only, no navigation, no `find_tab` | `google.com/sorry/index` → **stop the run**; tell the user Google served the unusual-traffic challenge and only a person can clear it in the browser. Do not answer it. Already-generated tabs are unaffected; only new navigations fail, so any rows already saved keep their files, and the rest stay `Pending`. Otherwise, a signed-out session and a non-Korean UI look identical in the log — re-check Step 0.4 on that tab and stop with the named cause. |
| `send did not take for <f>; retrying once` | Nothing — the script refills and resends once, then re-verifies with `SUBMITTED_JS` (conversation URL **and** an answer that has started; a `/app/<id>` URL alone is not proof) | Resend succeeded → continue. `send never took` / `resend failed` → row stays `Pending`, no `slot`; resubmit in Step 4. |
| `sweep N: k still generating` | Normal. Sweeps run every ~3.5–7s (jittered around `SWEEP_INTERVAL` 5) and poll all slots concurrently; a slow slot never blocks the others | Let it run. Never wait out one slot in place. |
| `<f>: no answer started — dropping it so it stops spending the budget` | This is the `DEAD_ROW_GRACE` (75s) dead-tab rule: the tab shows neither an image nor "Creating your image" | The script sets `last_error` and **removes `slot`**, so this row is *not* collectable — it must be **resubmitted** (Step 4, plain re-run), regardless of the closing "re-run with `--collect-only`" hint. |
| `<f>: extraction failed, retrying next sweep` | Transient; the row stays in the sweep and the overall deadline bounds the retries | Let it run. |
| `viewer never opened (no-image / no-button / <blank>); reading the rendered image for this row only` | Per §4 this is that one row's bad luck, **not** a browser setting; later rows still get their chance at the original | Let the run finish. That row lands at ~1024px and will be named in the `**` line. Recovery in Step 4. |
| `the browser refused the download; … not attempting it again this run` | A control that was clicked and produced no file. From here on **every** remaining row is a 1024px canvas copy | Let the run finish (files are still saved and the manifest still completes), then check the browser's automatic-downloads setting for `gemini.google.com` before any re-run for originals. Do not fight it mid-run. |
| `saved <f> … ** ratio off, review this row` | Drift > 4% from the row's `aspect_ratio` | That row needs a **resubmit, not a footnote** (§5.2). Step 4. |
| `<f>: not ready before the deadline — left Pending` | Deadline expired with tabs still open and `slot` still recorded | Step 3-bis: re-run with `--collect-only` — the tabs hold their images and nothing has to be regenerated. Alternatively raise `--deadline`. **Do not lower `--batch`** on this evidence (§7). |
| `finished inside the deadline with k row(s) unsaved — re-run with --collect-only` | Cross-check against the log: rows that still carry `slot` in the manifest are collectable; a row dropped by the dead-tab rule is not | Collectable → Step 3-bis. Dropped → resubmit. |

### Step 3-bis — collect-only re-run (only when rows are unsaved *and* still carry `slot`)

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/demo/images/image_prompts.json --collect-only
```

Runs in a fresh process, reads each row's recorded `slot` and sweeps only those
tabs; rows without a recorded `slot` are named in a "no recorded slot for …"
line and must be resubmitted instead. Because it is a fresh process,
`_download_refused` starts `False` again, so a row demoted by a one-off viewer
failure gets another shot at the original.

## Step 4 — Repair rows that finished wrong (only if any did)

There is no flag for redoing a `Generated` row (§3). By hand, in the manifest:

- **Ratio off**, or an unwanted 1024px file: set that row's `status` back to
  `"Failed"`, delete its output file, then re-run the Step 1 command. It is
  `Failed`, so it is retryable; it has no `slot`, so it is resubmitted into a
  fresh tab.
- **`viewer never opened` on that row only**, and I still want the original
  without regenerating: set `status` to `"Failed"` **and** restore its `slot`
  to the 0-based number I wrote down in Step 2 (tab group
  `agent:ppt-master-image-3` ⇒ `"slot": 2`), then run the `--collect-only`
  command. Its tab still holds the finished image.
- **Download refused for the whole run**: fix the browser's automatic-downloads
  permission for `gemini.google.com` first — otherwise the re-run degrades the
  same way.

Rows this skill cannot finish stay `Pending`. Hand them back to the caller with
the manifest as the record; the fallback-to-another-image-path decision is the
caller's, not this skill's.

## Step 5 — Verify before reporting success (§5). All five, in order.

```bash
# 5.1  every row Generated, every file present
cat projects/demo/images/image_prompts.json
ls -l projects/demo/images/*.png
```
All 4 rows must read `Generated` with no `last_error`, and each `filename` must
exist in `projects/demo/images/`.

**5.2 Ratio within 4%.** The script prints `** ratio off, review this row`;
an absent note is the pass. Cross-read the saved lines: 16:9 should come back
2752×1536 (1.792 vs 1.778, ~0.8% drift) and 4:3 should come back 2400×1792
(1.339 vs 1.333, ~0.4%) — both inside `RATIO_TOLERANCE`.

```bash
# 5.3  no two outputs share a checksum
shasum -a 256 projects/demo/images/*.png | awk '{print substr($1,1,12), $2}' | sort
```
Four distinct digests. A duplicate means slot isolation broke — the whole run is
void: set the affected rows back to `Failed`, close every slot tab, and redo it.

**5.4 Resolution.** No file may be 1024px on its long edge, since
`--displayed-size` was not asked for. Ratio and checksum both pass on a canvas
copy, so this is the only check that catches silent degradation. The run prints
a `**  N of M row(s) fell back to the 1024px rendered copy…` line naming the
rows; **an absent line is the pass.** Confirm long edges of 2752 (16:9) and
2400 (4:3).

```bash
# 5.5  no leftovers
ls ~/Downloads/Gemini_Generated_Image_* 2>/dev/null || echo "clean"
```
Must print `clean`. A leftover partial is read as the next row's file.

## Step 6 — Cleanup and report

Only once all four rows read `Generated` and Step 5 passes: offer to clear the
clutter — `close_tab` on each of `ppt-master-image-1` … `ppt-master-image-4`,
which removes the tab and its group. **Do not close them earlier**: a
`--collect-only` rerun needs those tabs, and so does the per-row original
recovery in Step 4.

Report to the caller: 4/4 rows `Generated` in `projects/demo/images/`, their
dimensions and ratios, elapsed time against the 300s deadline, and — explicitly
— whether any row fell back to the 1024px copy. Any row still `Pending` is
handed back with its `last_error`, and the choice of a different image path is
left to the caller.
