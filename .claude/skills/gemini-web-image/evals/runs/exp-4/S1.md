## 2. The run command

```bash
cd /Users/jaehyeonroh/Desktop/Personal/slide-master && \
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/demo/images/image_prompts.json
```

Foreground, with the Bash tool timeout raised to **400000 ms** so the script's
own 300s deadline is what ends the run, not my tool call. (At the 120s default
my call would return first and I would lose the log while the browser kept
working.)

### Flag decisions

| Flag | Decision | Why |
|---|---|---|
| `--manifest` | `projects/demo/images/image_prompts.json` | Required |
| `--output` / `-o` | **omitted** | Default is the manifest's folder, which is where the ppt-master contract expects `images/<filename>` |
| `--batch` | **omitted** (default covers all 4) | All four rows go in one pass. Splitting only repeats the per-row submission cost, and the one reason to lower it — Google's unusual-traffic challenge — is a ten-tab-scale risk, not a four-tab one. Four is well under the batch size that ever tripped it |
| `--generate-wait` | **omitted** | The pre-wait is dead time; sweeping early costs one cheap probe per slot, and a slot still generating is skipped and re-checked next sweep |
| `--deadline` | **omitted** (300s) | Budget for 4 rows: ~10s serial submit per row (~40s + jitter), then ~12s serial download per row (~48s), plus generation that mostly overlaps (rows typically ready 20–50s after submit). ≈ 110–150s expected — comfortable inside 300s with margin for one slow generation |
| `--displayed-size` | **omitted** | This trades the original (2752×1536 for 16:9) for the 1024px canvas copy to buy back ~12s/row. With ~150s of headroom against the deadline, there is nothing to buy. Full resolution wins |
| `--collect-only` | **omitted** | The tabs do not exist yet. This flag is a recovery path only (§7.1) |

I run the command **once**. No concurrent second invocation, and I do not touch
the browser while it runs.

## 3. What the script does, so I know what a healthy log looks like

1. `require_daemon()` → `list_tabs`.
2. Reads manifest, filters `status != "Generated"` → 4 rows. (No `rows pending;
   taking N this pass` line, since 4 ≤ batch.)
3. `submitting 4 prompt(s), one tab each` — then per row, in order, session
   `ppt-master-image-1..4`: `navigate` to `https://gemini.google.com/images`
   with `newTab: true` (never `/app`), dismiss `사용해 보기` onboarding if
   present, find the prompt box, `fill`, wait for `메시지 보내기` to render,
   click it (never Enter — the bridge has no key-press tool), then **verify the
   send actually took** (conversation URL *and* the answer started). Jittered
   pauses throughout.
4. Writes `slot` back into each submitted row and saves the manifest —
   immediately, before any image exists.
5. `4 submitted in Ns; settling 10s before the first sweep`.
6. `collect()` sweeps **all four slots concurrently** every ~5s (jittered),
   forcing the lazy decode (`loading='eager'` + `img.decode()`), and for each
   slot that is decoded: opens the viewer by clicking the result `<img>`'s
   parent `<button>`, finds `원본 크기 이미지 다운로드`, clicks it, waits up to
   25s for a new `~/Downloads/Gemini_Generated_Image_*`, copies it to
   `projects/demo/images/<filename>`, deletes every download newer than the
   click, closes the viewer, and writes the manifest back with
   `status: "Generated"` and `slot` removed.

Healthy final line: `saved 4 this run · manifest 4/4 · ~140s elapsed (within
the 300s deadline)` and no `over budget` line after it.

## 4. Decision points during submission (log lines from `submit()`)

Everything here is per-row. A row that fails submission is simply not in
`slots`, gets no `slot` key, and stays `Pending` — the other three continue.

| Log line | What it means | My branch |
|---|---|---|
| `submitted <file> (16:9)` / `(4:3)` | Row is in its tab and answering | Continue |
| `navigate failed twice for <file>` | Bridge refused the navigation twice (2s apart) | Let the run finish for the other rows, then rerun the plain command (§7.2). No `slot` was recorded, so `--collect-only` cannot help this row |
| `prompt box never appeared for <file>` — **on every row** | Three possible causes and the log cannot tell them apart | **Read the URL before blaming anything.** See §5.2 |
| `prompt box never appeared` on **one** row only | Transient page load | Rerun the plain command afterwards for that row |
| `fill failed` / `send click failed` | Bridge action refused | Same as above: rerun plain for that row |
| `send button never appeared` | The button renders only once the box holds text, so the fill may have silently not landed — or the UI language is wrong and the prompt box matched by luck | Check UI language (§5.2) if it repeats; otherwise rerun plain for that row |
| `send did not take for <file>; retrying once` | A conversation URL alone is not proof — the body was still blank. The script re-fills and re-clicks by itself | Nothing to do; watch for the next line |
| `send never took for <file> — leaving it Pending` / `resend failed` | Both attempts dropped | Row stays `Pending` with no slot → rerun plain (§7.2) |

If **all four** rows fail submission, the script still proceeds to `collect()`
with an empty slot list and exits quickly. That is the signal to go to §5.2, not
to rerun blindly.

## 5. Decision points during collection

### 5.1 `sweep N: M still generating`
Normal. A slot that is still generating is skipped and looked at again next
sweep; it never blocks the others. I do nothing — in particular I do not open,
reload, or navigate that tab, because the tab already holds (or will hold) the
finished image and re-opening the conversation is what makes it decode slowly or
bounce to `/app`.

### 5.2 `prompt box never appeared` on every row → check the URL, not the UI
Three causes look identical in the log: signed out, non-Korean UI, and Google's
unusual-traffic challenge. The URL separates them. After the run has stopped, I
read one failed slot's URL through the bridge on that slot's own session
(`evaluate` of `location.href` on `ppt-master-image-1`, or `list_tabs` on that
session) — **never `find_tab`**, which returns `"ok": true` without switching
tabs and has already caused one image to be written under four names.

- URL contains `google.com/sorry/index` → Google's anti-bot interstitial. There
  is no prompt box there, so every submission after it fails. **Stop. Do not try
  to answer or bypass the challenge.** Tell the user it must be cleared by a
  person in the browser, note that already-generated tabs are unaffected (only
  new navigations hit it), and that the remaining rows stay `Pending`. On the
  rerun after they clear it, lower `--batch` — but with only 4 rows there is
  nothing left to lower, so the mitigation is simply to space the reruns out.
- URL is a Gemini page but signed out (no prompt box, no account chip) → stop
  and report the precondition.
- Signed in, Korean-looking page, still no match → the UI language is not
  Korean. Stop; the five accessible-name patterns must be re-read from a live
  page. Do not guess them.

### 5.3 `<file>: no answer started — dropping it so it stops spending the budget`
The tab showed neither an image nor "Creating your image" for 75s: the send was
dropped and the conversation opened blank. This is a **dropped** row, not a slow
one, and dropping it is correct — two such rows once ate an entire run's budget.
Its `last_error` says "resubmit this row". Branch: after the run, resubmit it
with a plain rerun (§7.2). Do **not** use `--collect-only` for it — the row
still carries its `slot`, so a collect pass would just re-read the same empty
tab.

### 5.4 `viewer download did not produce a file; reading the rendered image instead, and not attempting it again this run`
The browser refused the download (or it did not land inside 25s), so this row
and **every row after it** get the 1024px canvas copy instead of the original —
the flag is global for the rest of the run. Branch:

- If the deck can live with 1024px: let the run finish, note the resolution in
  my report.
- If originals are needed: let the run finish, then tell the user to allow
  automatic downloads for `gemini.google.com` in the browser's site settings,
  flip the affected rows' `status` back to `Pending`, and rerun the plain
  command. I do not change browser settings myself.

Conversely, `original file via the viewer download (Ns)` on all four rows is the
line that proves the viewer step worked. If every row lands at 1024px **and**
this line never appears, the viewer step failed — not the browser.

### 5.5 `<file>: extraction failed, retrying next sweep`
Kept in the sweep on purpose; the overall deadline bounds the retries. I do
nothing unless it repeats to the deadline, at which point it is a §7.1 case.

### 5.6 `saved <file> WxH ratio R vs 16:9 (N bytes) [sweep S, read at Ts, gemini done at Gs, lag Ls]`
Expected sizes: 16:9 → 2752×1536 (ratio 1.792 vs target 1.778, ~0.8% drift);
4:3 → 2400×1792 (ratio 1.339 vs target 1.333, ~0.45% drift). Both are inside the
4% tolerance, so **no `** ratio off` note is expected on any of the four rows.**

- `** ratio off, review this row` appears → that row needs a **resubmit, not a
  footnote** (§7.3).
- A large `lag` (gemini finished long before we read it) is a detection problem
  on our side, not generation latency on Gemini's — worth reporting, not
  worth re-running for.

### 5.7 `<file>: not ready before the deadline — left Pending`
The 300s wall clock expired. Rows keep their `slot` and their `last_error`; the
tabs are still open. → §7.1.

### 5.8 `over budget — lower --batch and re-measure`
Printed when the run exceeded the deadline **or** when `saved != submitted`. So
it also fires on a within-deadline run that lost a row. I read the per-row lines
above it rather than reacting to this line alone; with 4 rows, "lower `--batch`"
is not the real remedy.

## 7. Recovery branches

### 7.1 Rows left `Pending` with a `slot` still recorded, tabs still open
(Deadline expiry, or repeated extraction failure.) The images may well be
finished and sitting in their tabs. Rerun **collect-only** — a fresh process
that skips submission and reads the slots already open:

```bash
cd /Users/jaehyeonroh/Desktop/Personal/slide-master && \
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/demo/images/image_prompts.json --collect-only
```

This works only because each submitted row wrote its `slot` down. I never
re-derive slot numbers: by now some rows are `Generated`, so re-numbering the
survivors would point row 3 at row 1's tab and save row 1's image under row 3's
name. If the script prints `no recorded slot for <files>`, those rows were never
submitted — resubmit them (§7.2) instead of collecting.

**Do not close any tab before this step.** A `--collect-only` rerun needs them.

### 7.2 Rows left `Pending` with **no** `slot` (submission failed, or dropped as dead)
Rerun the plain command from §2. Only non-`Generated` rows are taken, so the
rows already saved are untouched and their files are not redone. Each resubmit
opens a fresh tab in its session.

### 7.3 A row saved with `** ratio off`
The row is already marked `Generated` and its `slot` was removed. To resubmit
it I edit that row's `status` back to `"Pending"` in
`projects/demo/images/image_prompts.json`, then rerun the plain command from
§2. I say so before editing, since it discards a saved file.

### 7.4 Rows the skill cannot finish
They stay `Pending`, and the manifest is the record. I hand them back to the
caller with their `last_error` verbatim rather than retrying indefinitely — this
skill does not choose a different image backend on its own.
