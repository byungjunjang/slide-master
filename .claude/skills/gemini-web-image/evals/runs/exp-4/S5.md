# S5 — three rows submitted, one row's `naturalWidth` never leaves 0

Scenario: 3 `ai` rows submitted, collection underway. Slots 1 and 2 give up their
image. Slot 3 shows an `<img>` whose `src` is a `blob:` URL, but every poll reads
`naturalWidth` 0. Finish the run and report.

Throughout, `<name>` is the project folder the caller named. Every other part of
every command is literal. All paths are absolute because the shell's working
directory is not assumed.

---

## 0. State this plan starts from

The run in flight was launched as:

```bash
python3 /Users/jaehyeonroh/Desktop/Personal/slide-master/.claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest /Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/image_prompts.json
```

No `--batch` (default 10 covers 3 pending rows in one pass), no
`--generate-wait` override (default 10s), no `--deadline` override (default 300s
measured from process start), no `--displayed-size` (the viewer download gives
the original file).

Facts that follow from that launch and that the rest of the plan depends on:

- Sessions are `ppt-master-image-1`, `-2`, `-3` for slots 0, 1, 2. Each session
  owns one tab; nothing else can move it.
- Each submitted row carries `slot` in the manifest, written back right after
  submission. A row that saves has `slot` popped and `status` set to
  `Generated`, and the manifest is rewritten on every save, so what already
  finished survives anything that happens next.
- The daemon precondition passed (`require_daemon` ran), the browser is signed
  in, and the UI is Korean — all three are proven by three prompts having been
  accepted, so none of them is re-checked now.
- Three Chrome tab groups exist, `agent:ppt-master-image-1` through `-3`. That
  clutter is expected and is cleaned up only at step 6.

## 1. Do not touch the browser while the sweep is running

Decision: **let the collection loop run to its deadline. Take no manual action
on any slot.**

Why: the sweep already applies the exact fix this symptom calls for. `READY_JS`
runs on every slot on every sweep and, whenever the blob image reads
`naturalWidth < 300`, sets `img.loading = 'eager'`, calls
`scrollIntoView({block: 'center'})`, and calls `img.decode()`. There is nothing
to add by hand, and the things I could do by hand are the ones the skill
forbids: never navigate a slot after submitting, never use `find_tab`, never
block on one slot while the others wait.

What the loop will do with this row specifically:

- The probe returns `present: true`, therefore `alive` is true, therefore the
  `DEAD_ROW_GRACE` (75s) drop path does **not** fire. This row is not treated as
  a dropped submission; it stays in `remaining` and is re-polled every sweep at
  the jittered 5s cadence (3.5–7s).
- `decoded` stays false, so `export_to` is never called for it — the row never
  reaches the viewer-download or canvas step at all.
- Slots 1 and 2 save; each save costs ~12s of serial download inside the loop,
  during which slot 3 simply is not polled. That is normal.
- At 300s the loop exits and the row gets
  `last_error: "gemini-web: still generating when the deadline expired"` and
  stays `Pending`.

Expected log tail:

```
  saved <file1>.png 2752x1536 ratio 1.792 vs 16:9 (… bytes) [sweep N, read at …s, gemini done at …s, lag …s]
  saved <file2>.png … 
  sweep N: 1 still generating          (repeating)
  <file3>.png: not ready before the deadline — left Pending
saved 2 this run · manifest 2/3 · 300s elapsed (within the 300s deadline)
over budget — lower --batch and re-measure. …
```

Reading of that last advisory line: it fires on `elapsed > deadline` **or**
`len(slots) != saved`. Here it is the second condition — 3 submitted, 2 saved.
Elapsed is not over budget and the batch size is not the problem, so I do
**not** lower `--batch` on the strength of that line. The line's own second
sentence is the applicable one: a tab showing a finished answer is a detection
problem, not a generation one — which is what step 2 goes to establish.

## 2. One read-only probe of slot 3 to classify the symptom

Per §7, the first question for `naturalWidth` stuck at 0 is whether the answer
is still rendering or already finished, and the tab's URL is read rather than
guessed at. The sweep log does not print per-slot `finished` vs `decoded` for a
row that never saves, so this is read directly.

Read-only means: `evaluate` only. No `navigate`, no `click`, no `find_tab`, no
reload. The body goes through a file, never inlined, because an inlined JSON
body loses non-ASCII text and breaks on quoting.

```bash
cat > /private/tmp/claude-501/-Users-jaehyeonroh-Desktop-Personal-slide-master/84f5215d-d6d7-4175-b330-d135e8d7f42c/scratchpad/probe3.json <<'JSON'
{"action":"evaluate","session":"ppt-master-image-3","args":{"code":"(() => { const img = [...document.querySelectorAll('img')].find(i => i.src.startsWith('blob:')); return JSON.stringify({url: location.href, creating: document.body.innerText.includes('Creating your image'), present: !!img, complete: img ? img.complete : null, nw: img ? img.naturalWidth : null, nh: img ? img.naturalHeight : null, box: img ? [img.offsetWidth, img.offsetHeight] : null, lazy: img ? img.loading : null}); })()"}}
JSON

curl -s -m 120 -X POST http://127.0.0.1:10086/command \
  -H "Content-Type: application/json" \
  --data-binary @/private/tmp/claude-501/-Users-jaehyeonroh-Desktop-Personal-slide-master/84f5215d-d6d7-4175-b330-d135e8d7f42c/scratchpad/probe3.json
```

Branches on what comes back:

| Reading | Meaning | Branch taken |
|---|---|---|
| `url` contains `google.com/sorry/index` | Google's unusual-traffic challenge | **Stop.** Do not attempt to answer or bypass the challenge. Tell the user it is there and that only a person can clear it in the browser. The two saved rows are unaffected; only new navigations are. Skip steps 3–5, go to step 6 reporting 2/3 with this as the cause. |
| `creating: true` | Gemini is still rendering the answer; not a decode problem | Go to step 3a — the row needs more wall clock, not more decoding. |
| `present: true`, `creating: false`, `nw: 0`, `box: [0, 0]` | The scenario as given: answer finished, result laid out at zero size, lazy decode never fired and did not fire after the sweep's `eager` + `decode()` either | Go to step 3b. |
| `present: false`, `creating: false` | Empty tab — the send was dropped and the conversation opened blank | This row is a resubmit, not a collect. The loop's dead-row grace would normally have dropped it; go straight to step 4 (resubmit), skipping the `--collect-only` rerun, because there is nothing in that tab to collect. |
| `lazy` still reads `lazy`, or `complete: false` | The sweep's mutation did not land on the element it should have | Same handling as step 3b — one `--collect-only` rerun re-applies it from a fresh process; nothing more to do by hand. |

I do **not** try to rescue this row with `--displayed-size`. The canvas fallback
selects on `i.complete && i.naturalWidth > 300`, so it needs the very decode that
is missing; it returns `no decoded image` for exactly this row. `--displayed-size`
trades resolution for time on rows that decode, and this row does not.

## 3. One bounded rerun, chosen by the branch

First confirm the rerun can identify the tab. `--collect-only` reads `slot` from
the manifest and refuses to guess:

```bash
python3 -c "import json; m=json.load(open('/Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/image_prompts.json')); [print(i['filename'], i['status'], i.get('slot'), i.get('last_error','')) for i in m['items']]"
```

Expected: two rows `Generated` with no `slot`, one row `Pending` with `slot` 2
and the deadline `last_error`.

- If the pending row shows `slot: 2` → the rerun will poll `ppt-master-image-3`,
  the correct tab. Proceed.
- If the pending row has **no** `slot` → `--collect-only` will log
  `no recorded slot for …` and collect nothing. Do not renumber it by hand —
  a resubmit is the only correct move. Skip to step 4.

### 3a. `creating: true` — more time

```bash
python3 /Users/jaehyeonroh/Desktop/Personal/slide-master/.claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest /Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/image_prompts.json \
  --collect-only --deadline 240
```

`--collect-only` skips submission entirely (no new navigation, so no new abuse
signal, and `--generate-wait` is not applied on this path). Only the one pending
row is taken, so the whole 240s belongs to it.

### 3b. Finished but undecoded — one more decode window

```bash
python3 /Users/jaehyeonroh/Desktop/Personal/slide-master/.claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest /Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/image_prompts.json \
  --collect-only --deadline 120
```

120s, not 240s: if `eager` + `decode()` has failed on every sweep of a finished
answer, more sweeps of the same element are unlikely to change anything, and the
budget is better spent on step 4. This rerun exists because it is cheap and
because it re-applies the fix from a fresh process against a page that has since
had more time to lay out.

Outcomes, either branch:

- Log shows `saved <file3>.png …` → the row is `Generated`, the manifest is
  written. Go to step 5.
- Log shows `<file3>.png: not ready before the deadline — left Pending` again →
  go to step 4.

## 4. At most one resubmit, then stop

A fresh generation is the only remaining lever that changes the image element
itself; sweeping the same tab cannot. Run one plain pass — no `--collect-only`,
so it submits:

```bash
python3 /Users/jaehyeonroh/Desktop/Personal/slide-master/.claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest /Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/image_prompts.json \
  --deadline 180
```

Two things to know before running it, both consequences of the row being the
only pending one:

- It is taken as index 0, so it is submitted into session `ppt-master-image-1`
  and the manifest's `slot` for it becomes 0. That replaces the tab currently
  holding row 1's result. This is safe **only because row 1 is already
  `Generated` and its file is on disk** — verify that in step 3's manifest dump
  before running this. If row 1 were still pending, this step would not be run.
- The prompt is rebuilt with the ratio first line, so the aspect ratio is
  re-requested; nothing is inherited from the stuck conversation.

If this pass also leaves the row `Pending`: **stop.** The row goes back to the
caller as `Pending` with its `last_error`. Do not switch to another image
backend from inside this skill — that decision belongs to the caller — and do
not report the row as anything other than unfinished.

## 5. Verify what actually landed before reporting anything

Run all four checks; a pass on the first alone is not enough.

```bash
# 1 + 2. statuses, files, and any ratio complaint
python3 -c "import json; m=json.load(open('/Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/image_prompts.json')); [print(i['filename'], i['status'], i.get('slot'), i.get('last_error','')) for i in m['items']]"
ls -l /Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/*.png

# 3. no two outputs share a checksum
shasum -a 256 /Users/jaehyeonroh/Desktop/Personal/slide-master/projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort

# 4. no leftovers from the download step
ls -la ~/Downloads/Gemini_Generated_Image_* 2>/dev/null || echo "no leftovers"
```

Decision points:

- **Every row that reads `Generated` must have its file on disk.** A `Generated`
  row with no file is a reporting error, not a partial success.
- **Ratio within 4%.** The run log prints `** ratio off, review this row` when it
  is not. A flagged row needs a resubmit, not a footnote in the report. If a
  saved row is flagged, resubmit it the same way as step 4 rather than shipping
  it.
- **Duplicate checksums between the two saved files mean slot isolation broke**
  and the whole run is redone from scratch. With one session per row and no
  `find_tab` anywhere this should not happen, but it is checked, not assumed.
- **Resolution.** Grep the run log for `original file via the viewer download`
  on both saved rows. If instead it logged
  `viewer download did not produce a file; reading the rendered image instead`,
  then the browser refused the download; that refusal is sticky for the rest of
  the process, so *both* saved files are the 1024px canvas copy. Report the
  smaller size explicitly rather than letting the caller assume originals.
- **Leftover `Gemini_Generated_Image_*` files.** A successful save clears every
  download newer than its click. If any remain (the run ended between click and
  cleanup), delete only files matching that glob that this run produced, so the
  next run's "newest since" test stays honest.

## 7. The report to the caller

State, in this order:

1. **Result: 2 of 3 rows `Generated`.** Name both files with their pixel
   dimensions and whether they are viewer-download originals or 1024px canvas
   copies. Name the third file as `Pending`.
2. **What the third row's tab actually showed** — the classification from step 2:
   a finished answer whose result element carries a `blob:` src but never
   decodes (`naturalWidth` 0, zero layout box), not a slow generation and not a
   dropped send. Quote its `last_error` from the manifest.
3. **What was tried, in order**: the sweep's own `loading = 'eager'` +
   `img.decode()` on every sweep for the whole deadline; one `--collect-only`
   rerun against the recorded slot; one resubmit (if step 4 ran) — and that each
   left the row unfinished.
4. **The manifest is the record.** The pending row keeps `status: "Pending"` and
   its `last_error`; nothing is marked `Generated` that has no file.
5. **No fallback was chosen.** This skill does not switch to another image path
   on its own; the caller decides whether to rerun this skill later, run
   `image_gen.py` on a host with a CLI/API backend, or drop the row.
6. **Tabs**: three groups `agent:ppt-master-image-1..3` are still open because
   the pending row may be retried; offer to close them.
7. If the step 2 probe found `google.com/sorry/index`: say plainly that Google
   served its unusual-traffic challenge, that it must be cleared by a person in
   the browser, that no attempt was made to answer it, and that a lower
   `--batch` is the mitigation for the next run.
