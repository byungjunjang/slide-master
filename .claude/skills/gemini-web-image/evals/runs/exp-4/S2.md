   tab shows the account chip and a prompt box.

     run, not diagnosed after it.

   matches — `Gemini 프롬프트 입력`, `메시지 보내기`, `사용해 보기`,
   `원본 크기 이미지 다운로드`, `닫기`.
   - Not Korean → stop. Per §2 I re-read those patterns from a live page before
     anything else and never guess them; changing the regexes is a skill edit,
     not part of this run.
4. `~/Downloads` is clean of stale artifacts:
   `ls -la ~/Downloads/Gemini_Generated_Image_* 2>/dev/null`
   - Files present → move or delete them now. `newest_download()` only accepts
     files with an mtime after the click, so old ones cannot be mistaken for a

5. Automatic downloads for `gemini.google.com` (optional): if it is not allowed,
   the run still finishes through the canvas fallback at 1024px. I do not block
   on this, but I note it, because it decides which log line I expect in Step 4.

## Step 2 — Route decision: `--collect-only` first, or straight to submission

The rule I am obeying: a submitted row carries `slot` in the manifest, and a row
without one is resubmitted, never guessed. Re-numbering survivors is what makes
row 3 read row 1's tab — and that hazard belongs to *collection*, not
submission, because a submit run rebinds its session to a brand-new tab.

- **Branch A — no `slot` on any of the 4 rows.** This is what I expect here:
  the script only writes `Generated` (and pops `slot` on success) or leaves a
  `last_error`; it never writes the string `Failed`. `Failed` with no `slot`
  therefore points at a different producer, or at rows that never got past
  `submit()`. There is nothing to collect and nothing whose tab I can identify.
  → Go to Step 3, a plain submit run. I do **not** pass `--collect-only`; it
  would print "no recorded slot for …" for all four and exit with
  "nothing to collect".
- **Branch B — the rows carry `slot` and those tabs are still open.** Confirm
  with `list_tabs` on `ppt-master-image-<slot+1>` for each: if the tab exists on
  a `gemini.google.com/app/<id>` URL, an image may already be sitting there from
  the earlier attempt. → Run the `--collect-only` pass in Step 3b **first**
  (cheap, no submission, no navigation), then submit whatever it could not
  harvest. I do not navigate or reload any of those tabs to inspect them — that
  is what makes a finished image slow to decode or bounce to `/app`.
- **Branch C — mixed.** Collect first (Branch B command, which skips rows with
  no `slot` and says so), then submit the remainder (Branch A command). Never
  the other way round: submitting first re-numbers slots and orphans the tabs
  the collect pass needed.

## Step 3 — The run

Before the command, one sentence to the user, once (§3): *this opens 4 Chrome
tabs in 4 groups named `agent:ppt-master-image-1` … `-4`; one group per row is
the isolation, and I will offer to clear them when every row is `Generated`.*

### 3a — Submit run (Branch A, and the tail of Branch C)

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --batch 4
```

Flag reasoning:

- `--batch 4` — all four in one pass. Splitting only repeats the ~10s-per-row
  submission cost, and four tabs is well under the ten-tab run that once tripped
  Google's unusual-traffic challenge. I pass it explicitly rather than relying
  on the default because SKILL.md documents the default as `4` and the script's
  `argparse` uses `10`; with 4 pending rows both take everything, but the flag
  makes the pass size a stated decision instead of an inherited one.
- No `--output` — the default is the manifest's folder, which is where the
  contract puts `images/<filename>`, and where the 2 existing files already are.
- No `--generate-wait` — the default settle is fine, and it is one pre-sweep
  wait, not per row.
- No `--deadline` — the default 300s is comfortable for 4 rows. Budget from
  §5.1: ~10s serial submit and ~12s serial download per row is ~88s, plus
  generation at 20–50s largely overlapping, so ~120–170s expected. There is no
  reason to trade resolution for time here.
- No `--displayed-size` — I want the originals (2752x1536 for 16:9), and the
  deadline is not tight. I would only reach for it if this run showed the whole
  set landing near 300s.
- No `--collect-only` — the rows have no identified tabs.

### 3b — Collect-only run (Branch B, and the head of Branch C)

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --batch 4 --collect-only
```

This skips submission entirely and reads slot *N* from each row rather than
recomputing it, which is the whole point: with 2 rows already `Generated`, any
re-numbering of the 4 survivors would aim them at other rows' tabs. Rows without
a `slot` are named in the log and skipped; they go to 3a.

## Step 5 — Second pass, only if some of the 4 did not finish

Split the unfinished rows by *why*, because the two causes take opposite
commands:

1. **Tab alive, answer started, just not read in time** (deadline expiry, or
   extraction still failing): the row kept its `slot`. → Rerun 3b
   (`--collect-only`). No submission, no re-numbering, no navigation. Raise
   `--deadline 600` if the first run died on the clock rather than on the page.
2. **No `slot`, or dropped as an empty tab**: the tab holds nothing worth
   reading. → Rerun 3a (plain submit). The script re-numbers these rows'
   slots from 0 and rebinds each session to a new tab via `navigate` with
   `newTab: true`, which is safe precisely because we are submitting; the
   re-numbering hazard only exists when reading tabs we did not just open.
3. **Both kinds present**: collect first, then submit. Running submit first
   would overwrite the `slot` values the collect pass depends on.

I do not close any tab between passes. §3 is explicit: a `--collect-only` rerun
needs those tabs, so nothing is closed until every row is `Generated`.

If a row still fails after one collect pass and one resubmit pass, it stays as
the manifest records it and I hand it back to the caller. I do not switch to a
different image backend from inside this skill.

   ```bash
   for it in m["items"]:

   ```
   Any row not `Generated`, or `Generated` with no file, is a failure to report,

2. Ratio within 4% of each row's `aspect_ratio`. The run log already printed
   `ratio X vs 16:9` and would have flagged `** ratio off`; I confirm no such
   marker appeared for the 4 new rows.
3. No two output files share a checksum — this sweep must include the 2
   pre-existing files, since a new row duplicating an old one is exactly the
   slot-leak signature this scenario is exposed to:
   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
   6 distinct prefixes → pass. Any repeat → slot isolation broke; the run is
   redone, not patched.
4. Downloads left clean:
   ```bash
   ls -la ~/Downloads/Gemini_Generated_Image_* 2>/dev/null
   ```
   The script deletes files newer than each click after a successful save, so
   this should list nothing. Leftovers get removed here.
5. Resolution sanity: the 4 new files should be original-size (e.g. 2752x1536
   for 16:9, 2048x2048 for 1:1). All four at 1024px means the viewer step never
   ran — check the log for `original file via the viewer download` before
