# S6 — the download control returns `{"ok": true}` and no file lands in `~/Downloads`

Goal: get this row's image into `<out_dir>/<filename>` and mark the row
`Generated`, without touching the tab that already holds the finished image.

Placeholders used below: manifest `projects/<name>/images/image_prompts.json`,
`out_dir` = the manifest's folder (no `--output` given), the failing row's
manifest `slot` value = `S`, so its bridge session is `ppt-master-image-<S+1>`
(`slot_name(index)` = `f"{SESSION_PREFIX}-{index + 1}"`, and the manifest stores
the zero-based `index`). Getting that off-by-one wrong reads another row's tab,
which is the exact failure the slot number exists to prevent.

---

## 0. State at the moment of the failure

- The row's generation succeeded. The image is in the slot's tab; the viewer is
  open on it; `DOWNLOAD_BUTTON_RE` (`원본 크기 이미지 다운로드`) matched, so the
  UI language is Korean and the viewer step worked.
- Only the file transfer failed. `export_to()` is mid-flight for this row.
- `{"ok": true}` from `click` is worth nothing here. SKILL.md §4: *this bridge
  reports success for actions it did not perform — `find_tab`, `click`, and
  `navigate` all do it. Verify the effect — the tab's URL, the file on disk —
  never the return value.* A new `~/Downloads/Gemini_Generated_Image_*` is the
  only proof a download happened.

## 1. Constraints that bound every step below

| Constraint | Consequence for this scenario |
|---|---|
| Never navigate a slot after submitting | No reload, no re-opening the conversation, no `--collect-only` restart *before* the fallback. The tab already holds the image; re-opening it is what makes it slow to decode or bounce to `/app` |
| Never use `find_tab` | The slot session `ppt-master-image-<S+1>` is the only way I address this tab |
| Give the download real time to land | The original is a multi-megabyte PNG, 11–17s click-to-file. `DOWNLOAD_WAIT = 25` one-second polls. I do not call it refused before those 25s are spent |
| Clear every file newer than the click | One click can produce more than one file, and the "newest since" test for the next row depends on it |
| Close the viewer afterwards | A viewer left open hides the next probe (`VIEWER_CLOSE_RE`, `닫기`) |
| Send every bridge body as a file | Any hand-issued bridge call uses `curl --data-binary @<tmp>.json`, never an inlined body |
| Vary every wait | Any hand-driven polling jitters (`human_pause`), never a metronome |

**Not on the table:** resubmitting the row. The failure is downstream of
generation — the image exists. A resubmit costs ~10s of submit plus a fresh
generation and returns a *different* image. Also not on the table: clicking the
download control a second time. The script makes one attempt per row by design,
and a browser that refuses one download refuses them all.

---

## 2. Step by step

### Step 1 — spend the full `DOWNLOAD_WAIT` before believing the failure

Poll for a `Gemini_Generated_Image_*` newer than the click, once a second, up to
25 times (this is what `export_to` does; the loop below is the hand equivalent
if I am driving the bridge myself):

```bash
# stamp taken immediately before the download click
STAMP=/private/tmp/claude-501/-Users-jaehyeonroh-Desktop-Personal-slide-master/84f5215d-d6d7-4175-b330-d135e8d7f42c/scratchpad/s6-click-stamp
find ~/Downloads -maxdepth 1 -name 'Gemini_Generated_Image_*' -newer "$STAMP" -print
```

**Branch A — a file appears within the 25s.** It was slow, not refused. Confirm
it is finished before copying: read `st_size`, wait 1s, read it again; equal
means the write is done. Then copy the bytes to
`projects/<name>/images/<filename>`, delete every `Gemini_Generated_Image_*`
newer than the stamp, close the viewer, and continue at Step 5 with the original
(2752x1536-class) file. Nothing else in this plan applies.

Note the script's sharp edge here: if the file is *still growing* at the 1s
recheck, `export_to` does not wait — it falls straight through to the refusal
path and leaves the partial in `~/Downloads`. If I see that (size still
climbing), I let the write finish by hand, copy it, remove the partial, and
treat this as Branch A rather than a refusal.

**Branch B — nothing matching the glob.** Widen the check once, because the
script's glob is the only thing it can see:

```bash
find ~/Downloads -maxdepth 1 -newer "$STAMP" -print
ls -lt ~/Downloads | head -20
```

- Something landed under a different name → the script will never find it. Copy
  it by hand to `projects/<name>/images/<filename>`, verify the PNG magic and
  dimensions, and continue at Step 5.
- A partial / in-progress file is present → the download is running, not
  refused. Wait it out inside the remaining `--deadline`, then Branch A.
- Genuinely nothing newer than the stamp → the browser refused the download.
  This is the optional precondition in §2 not being met: `gemini.google.com` is
  not allowed under the browser's automatic-downloads setting. Go to Step 2.

I do not touch anything in `~/Downloads` older than the stamp — that is the
user's data, not this run's.

### Step 2 — restore the tab to its pre-click state

Snapshot the slot session, find `VIEWER_CLOSE_RE` (`'role': 'button', 'name':
'닫기'`), click it, re-snapshot to confirm it is gone.

- `닫기` present and gone after the click → proceed.
- `닫기` never in the tree → the viewer did not actually open, or the UI is not
  Korean. Both contradict the fact that the download button matched, so I stop
  and report the inconsistency rather than guessing a selector. Do not fabricate
  refs.

The viewer must be shut before the canvas readback: `CANVAS_JS` takes the first
`blob:` image with `naturalWidth > 300`, and I want the inline result, not a
viewer-scaled copy.

### Step 3 — record the refusal for the rest of the run

Set `_download_refused = True` (the script does this automatically once the
first row's download fails to produce a file) and log the line the skill's §7
table keys on:

```
viewer download did not produce a file; reading the rendered image instead,
and not attempting it again this run
```

Every later row skips the viewer download and goes straight to the canvas. That
is deliberate and I do not defeat it: the attempt costs 25s of a 300s budget per
row, and a browser that refuses one refuses them all.

### Step 4 — take the canvas copy

**4a. Force the decode first.** Evaluate `READY_JS` on
`ppt-master-image-<S+1>` and read the JSON it returns
(`present` / `creating` / `finished` / `decoded`):

| Reading | Branch |
|---|---|
| `decoded: true` | Go to 4b |
| `finished: true, decoded: false` | The result is laid out at zero size and its lazy decode never fired. `READY_JS` already set `loading = 'eager'`, called `scrollIntoView`, and kicked `img.decode()`; it resolves before the next sweep, so re-probe on the next sweep rather than blocking. Scrolling alone cannot fix a zero-box element |
| `creating: true` | The answer is still rendering — but the download button was in the tree, which means it was finished. If this really reads `creating`, keep sweeping; do not extract yet |
| `present: false, creating: false` | Not a download problem: the tab is empty, the send was dropped. `DEAD_ROW_GRACE = 75s` of this state and the row is dropped with `last_error` "conversation opened but no answer ever started; resubmit this row" and handed back for resubmission |

**4b. Read the canvas.** Evaluate `CANVAS_JS`, which draws the decoded `blob:`
image into a canvas at `naturalWidth` x `naturalHeight`, stashes
`window.__pptMasterGrab` as a `data:image/png;base64,…` URL, and returns
`{len, w, h}`.

- `{error: 'no decoded image'}` → `export_to` returns `()`; the row stays in the
  sweep with `last_error = "gemini-web: image could not be extracted yet"` and
  is retried next sweep. Not dropped — the overall deadline bounds the retries.
- `{len, w, h}` → pull it in `CHUNK = 600_000`-character slices:
  `(() => window.__pptMasterGrab.slice(<offset>, <offset+600000>))()`, repeating
  until `offset >= len`. An empty piece breaks the loop early → treat as a
  failed extraction, same as above, retry next sweep.

**4c. Write the file.** Assert the joined string starts with
`data:image/png;base64,`; if it does not, the extraction failed — retry next
sweep. Otherwise base64-decode and write to
`projects/<name>/images/<filename>`.

Expect a ~1024px-class image, not 2752px. That is the documented cost of the
fallback and it is the whole point of §2's "without it the canvas fallback still
finishes the run at the displayed size."

### Step 5 — ratio check and manifest write

`actual = width / height`; `drift = |actual - target| / target` against the row's
`aspect_ratio`; tolerance `RATIO_TOLERANCE = 0.04`.

- Within 4% → set `status = "Generated"`, pop `last_error`, pop `slot`, and
  write the manifest immediately (an interrupted run keeps what it finished).
- `** ratio off` → §5 says that row needs a resubmit, not a footnote. The canvas
  copy preserves the source ratio (`naturalWidth`/`naturalHeight`), so a ratio
  miss here means Gemini returned the wrong shape, not that the fallback
  distorted it. Flag it for resubmission.

**Before I let Step 5 run, one decision point I surface to the caller if the
deck's resolution matters:** saving now marks the row `Generated` and pops its
`slot`. A later run cannot upgrade it to the original — `pending` skips
`Generated` rows, and with `slot` gone a `--collect-only` pass cannot find its
tab, so the row would have to be reset to `Pending` and *resubmitted*, producing
a different image. If originals are required, the cheaper order is: pause, have
the user allow automatic downloads for `gemini.google.com`, and re-collect from
the still-open tabs before anything is saved. The scenario asks for the image in
the file, so absent that instruction I take the canvas copy and report the
tradeoff.

### Step 6 — the rest of the run

Remaining rows sweep on `SWEEP_INTERVAL = 5` (jittered 3.5–7s) and take the
canvas path directly, so each saves the ~25s the refusal cost this row.

If the `--deadline` (300s from process start) expires first, unfinished rows are
left `Pending` with `last_error = "gemini-web: still generating when the
deadline expired"`. Re-collect from the tabs that are still open, skipping the
doomed download attempt entirely:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --collect-only --displayed-size
```

`--collect-only` reads each row's recorded `slot`; rows without one were never
submitted from this manifest and get resubmitted, never guessed.
`--displayed-size` presets `_download_refused = True` so a fresh process does
not re-spend 25s discovering the same refusal.

Do not close any slot tab until every row is `Generated` — a `--collect-only`
rerun needs them. When the run is done, offer to clear the clutter: `close_tab`
on each `ppt-master-image-N` session removes the tab and its
`agent:ppt-master-image-N` group.

## 3. Decision tree, condensed

```
download click returns ok
 └─ poll ~/Downloads for Gemini_Generated_Image_* newer than the click, 25 x 1s
     ├─ file lands, size stable after 1s ─→ copy to out_dir/<filename>,
     │                                       delete files newer than click,
     │                                       close viewer, ratio check, Generated
     ├─ file lands, still growing ────────→ let it finish by hand, then as above
     ├─ file under another name ──────────→ copy it by hand, then as above
     ├─ partial in progress ──────────────→ keep waiting inside the deadline
     └─ nothing at all (25s spent) ───────→ browser refused
          └─ close viewer (닫기) ─→ mark _download_refused ─→ READY_JS
               ├─ decoded ────────→ CANVAS_JS ─→ chunked slices ─→ write file
               │                     └─ no decoded image / short read
               │                         ─→ last_error, retry next sweep
               ├─ finished, not decoded ─→ eager+decode() fired, re-probe
               ├─ creating ──────────────→ keep sweeping
               └─ nothing present ───────→ 75s grace, then hand back to resubmit
```

## 4. Verification before reporting success (§5)

1. The row reads `Generated` and `projects/<name>/images/<filename>` exists.
2. Its ratio is within 4% of the row's `aspect_ratio` — no `** ratio off`.
3. No two output files share a checksum (identical files mean slot isolation
   broke and the run must be redone):
   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
4. `~/Downloads` holds no leftover `Gemini_Generated_Image_*`:
   ```bash
   ls -l ~/Downloads/Gemini_Generated_Image_* 2>/dev/null
   ```
   The refusal path never creates one, but a partial from Branch B can survive —
   remove any file this run produced, leave anything older alone.
5. The run log shows the fallback line, not `original file via the viewer
   download`. That mismatch is the honest record of what happened.

## 5. What I report back

- The row is `Generated` and the file is on disk, taken from the rendered image
  rather than the downloaded original.
- It is the ~1024px displayed copy, not the ~2752px original; the ratio is
  correct either way.
- Cause: the browser refused the page's download. The optional precondition in
  §2 — `gemini.google.com` allowed under the browser's automatic-downloads
  setting — is not met on this host. That is a browser setting the user changes;
  I do not change it.
- To get originals: allow automatic downloads for `gemini.google.com`, then
  re-run. Those rows must be reset to `Pending` first and will be resubmitted
  (their `slot` was popped on save), so the re-run yields new images, not
  higher-resolution copies of these.
- Any row this path cannot finish stays `Pending` and goes back to the caller;
  the manifest is the record.
