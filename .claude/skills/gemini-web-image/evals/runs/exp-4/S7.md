# S7 — Reading row 3's image from a 4-row batch that is still generating

Situation: `gemini_web_image.py` submitted a 4-row batch; the images are
generating. The job is to read row 3's image.

All paths below are relative to the repo root
(`/Users/jaehyeonroh/Desktop/Personal/slide-master`); `<name>` is the project
folder holding the manifest.

---

## 0. The invariants that decide everything here

These are fixed before any command runs, and every branch below obeys them.

1. **A tab is addressed by its bridge session name, never by anything else.**
   One bridge session per row; the bridge scopes its "current tab" to the
   session name, so the session *is* the handle on row 3's tab. Every bridge
   command that touches row 3 carries `"session": "ppt-master-image-<N>"` and
   nothing else identifies the tab.
2. **Never `find_tab`.** It returns `"ok": true` without switching tabs; a loop
   built on it once wrote one image under four different file names. There is no
   condition in this scenario under which I call it.
3. **Never navigate, reload, or re-open row 3's conversation.** The tab already
   holds (or is producing) the finished image. Re-opening is what makes the
   image decode slowly or bounces the tab to `/app`.
4. **The slot is read from the manifest, never recomputed.** `slot` is the row's
   index inside the submitted batch (`pending[:--batch]`), written at submit
   time. Row 3 of `items` is *not* automatically slot 2: rows already
   `Generated` are excluded from `pending`, so the batch position can differ.
   A row with no `slot` is resubmitted, never guessed.
5. **Session name = `slot_name(slot)` = `ppt-master-image-{slot + 1}`.** The
   recorded slot is 0-based; the session suffix is 1-based. Off-by-one here
   reads another row's tab.
6. **Sweep, do not block.** Even when only row 3 is wanted, I do not sit on row
   3's tab in a blocking wait — that spends the budget the other three rows need,
   and single-pass waits have already reported finished images as failures.
7. **Do not close any tab** until all four rows read `Generated`; a
   `--collect-only` rerun needs those tabs and their groups.

---

## 1. Establish which tab is row 3's

```bash
python3 - <<'PY'
import json
p = 'projects/<name>/images/image_prompts.json'
m = json.load(open(p, encoding='utf-8'))
for i, it in enumerate(m['items'], 1):
    print(i, it['filename'], it['status'], it['aspect_ratio'],
          'slot=', it.get('slot'), it.get('last_error', ''))
PY
```

Read row 3's line. Decision point on its `slot` field:

| What row 3 shows | Branch |
|---|---|
| `status = Generated` | Nothing to read. Confirm `projects/<name>/images/<filename>` exists and stop. |
| `slot` is an integer *s* | Row 3's tab is session **`ppt-master-image-{s+1}`**. Write that name down and use it verbatim from here on. In the ordinary case where all four manifest rows were pending, row 3 carries `slot = 2` and its session is `ppt-master-image-3`. |
| `slot` is absent/null and status is `Pending`/`Failed` | The submit never took for this row (navigate failed, prompt box never appeared, or the send never took). **There is no tab to read.** Do not guess a session and do not read `ppt-master-image-3` on the assumption that "row 3 = slot 3" — that is exactly how row 3 gets saved with row 1's image. Resubmit instead (§5). |

I record the chosen session name explicitly before touching the bridge, because
every later step is just "run this command against that session".

## 2. Decision point: is the submitting process still running?

```bash
pgrep -fl gemini_web_image.py
```

- **Still running →** Branch A (§3).
- **Exited →** Branch B (§4).

This matters because the running process is already sweeping every slot
concurrently, including row 3's, and will export and save row 3 on the sweep
after its image decodes. Reading the same session out of band races it: my
viewer would be open (`원본 크기 이미지 다운로드` / `닫기` in the tree) while its
probe or export runs against the same tab, and both of us would be clearing
`~/Downloads/Gemini_Generated_Image_*` files newer than our own click.

---

## 3. Branch A — the run is still in flight (default branch for this scenario)

The scenario says the batch was submitted and images are generating, so this is
the expected state.

1. **Do not send any bridge command to `ppt-master-image-{s+1}`.** Row 3 is
   already being swept every ~5s (jittered 3.5–7s), concurrently with the other
   three slots.
2. Watch the run's own log lines for row 3's filename:
   - `saved <filename> WxH ratio ... [sweep n, read at Ts, gemini done at Gs, lag Ls]`
     → row 3 is written to `projects/<name>/images/<filename>` and the manifest
     row is already flipped to `Generated`, `slot` removed, and rewritten to disk
     immediately. Go to §6 (verify).
   - `sweep n: k still generating` → row 3 is not decoded yet; keep waiting.
   - `<filename>: extraction failed, retrying next sweep` → the export returned
     nothing; the row stays in the sweep and is retried. No action.
   - `<filename>: no answer started — dropping it so it stops spending the budget`
     → the tab showed neither an image nor "Creating your image" for more than
     75s. Row 3's tab is empty, not slow. Go to §5 (resubmit); do not try to
     rescue that tab by navigating it.
   - `<filename>: not ready before the deadline — left Pending` → the 300s
     wall-clock budget expired. The tab is still open and still holds the
     conversation, so go to Branch B.
3. If a per-row read is genuinely required *before* the process finishes (the
   caller wants row 3's bytes now, not the whole batch), then and only then use
   §7 — and accept that it interleaves with the running sweep. Otherwise I let
   the sweep do it, because the sweep also does the ratio check, the manifest
   write-back, and the `~/Downloads` cleanup that a hand read skips.

Nothing in this branch touches the browser at all. That is the point: row 3's
tab is addressed by owning session `ppt-master-image-{s+1}`, and the process
that owns it is already reading it.

## 4. Branch B — the process has exited and row 3 is still not `Generated`

Row 3's tab is still open (nothing closes tabs on exit). Re-enter through the
script's own collection path, which reads each row's recorded `slot` and sweeps
those sessions without submitting anything:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --collect-only
```

Why this and not a hand-written read of one tab:

- `--collect-only` maps each pending row to `ppt-master-image-{its recorded
  slot + 1}` from the manifest, which is exactly the addressing rule in §0.4–0.5,
  applied by the code rather than by me.
- It skips submission entirely, so it cannot navigate row 3's tab.
- It sweeps *all* the still-pending slots concurrently rather than blocking on
  row 3, which is what §0.6 requires. Picking up rows 1, 2 and 4 alongside row 3
  is correct behaviour, not collateral.

Expected log lines and the branch each implies:

| Line | Meaning / next step |
|---|---|
| `saved <row 3 filename> ...` | Done — go to §6. |
| `no recorded slot for <row 3 filename> — … Resubmit them instead of collecting.` | Row 3 has no tab to identify. Go to §5. |
| `nothing to collect` | No pending row has a slot; go to §5. |
| `nothing to do — every row is already Generated` | Row 3 was saved by the earlier run. Go to §6. |
| `<row 3 filename>: not ready before the deadline — left Pending` | Still generating. Re-run the same `--collect-only` command (a fresh process gets a fresh 300s budget). Row 3 keeps its `slot`, so the rerun addresses the same tab. |
| `** ratio off, review this row` on row 3 | The file saved, but the aspect ratio drifted >4% from `aspect_ratio`. This is a resubmit (§5), not a footnote. |

If the deadline is the binding constraint on the rerun, add `--displayed-size`
to trade row 3's original PNG for the 1024px canvas copy and buy back ~12s per
row. Only when the deadline matters more than the pixels — the default path is
the original.

## 5. Branch C — row 3 has no usable tab (no `slot`, dropped, or ratio off)

There is nothing to read; the correct action is to resubmit, and resubmission
re-establishes the slot→session mapping from scratch.

1. Do not close the other three tabs (§0.7).
2. Clear row 3's `status` back to `Pending` if it is `Failed`, and leave every
   `Generated` row alone.
3. Re-run without `--collect-only` so row 3 is submitted into a fresh tab and a
   fresh `slot` is written to the manifest:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

Note the consequence and accept it: this pass renumbers slots over the
*currently pending* rows, so row 3 may land in `ppt-master-image-1` even though
it was `ppt-master-image-3` before. That is fine precisely because the new slot
is written to the manifest; it is never inferred. The stale tabs from the old
run remain until §8.

## 6. Verify before reporting row 3 read

1. `projects/<name>/images/<row 3 filename>` exists and row 3 reads `Generated`
   with no `last_error` and no leftover `slot` key.
2. The saved PNG's ratio is within 4% of row 3's `aspect_ratio`. The run prints
   `** ratio off` when it is not; that is a resubmit (§5).
3. No two output files share a checksum — identical files mean slot isolation
   broke and the whole run is redone:

```bash
shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
```

4. `~/Downloads` holds no leftover `Gemini_Generated_Image_*`:

```bash
ls ~/Downloads/Gemini_Generated_Image_* 2>/dev/null
```

5. Sanity on the log line for row 3: it should say
   `original file via the viewer download (Ns)`. If it instead logged
   `viewer download did not produce a file; reading the rendered image instead`,
   the image is the 1024px canvas copy — the viewer step failed, not the browser,
   and row 3 should be re-read with a fresh `--collect-only` before accepting it.

## 7. Hand-reading row 3's tab (only if §3.3 forced it)

Every call below goes to the **same one session**, `ppt-master-image-{s+1}`,
posted as a file body (an inlined JSON body loses non-ASCII text and breaks on
quoting). No `find_tab`, no `navigate`, no `list_tabs`-based matching, no
URL or page-text inference — the session name is the whole addressing scheme.

1. **Probe readiness.** `evaluate` the skill's `READY_JS` in that session. It
   also fixes the common stall: it sets `img.loading = 'eager'`, scrolls, and
   calls `img.decode()`, because the result is routinely laid out at zero size
   and `scrollIntoView` on a zero-box element is a no-op. Read its JSON:
   - `decoded: true` → step 2.
   - `creating: true` (or `finished: true, decoded: false`) → still rendering or
     not yet decoded. Re-probe after a jittered ~3.5–7s pause. Do not block in a
     single long wait.
   - `present: false, creating: false` → the tab is empty, not slow. Also
     `evaluate` `location.href` in the same session: a
     `https://www.google.com/sorry/index?continue=…` URL is Google's
     unusual-traffic challenge — stop everything, tell the user, and let a
     person clear it in the browser; do not attempt to answer it. Otherwise, if
     the tab stays empty past ~75s, go to §5.
2. **Open the viewer before looking for the download control.** `evaluate` the
   skill's `OPEN_VIEWER_JS`, which clicks the `<button class="image-button">`
   wrapping the blob `<img>`. There is no download button beside the inline
   result; skipping this step is what silently produced 1024px files.
   - returns `opened` → step 3.
   - returns `no-image` / `no-button` → back to step 1; do not fall through to
     the canvas copy on a transient miss.
3. **Find the control.** `snapshot` the session and match the accessible name
   `원본 크기 이미지 다운로드`, retrying up to ~7 times with 0.35–0.8s jitter while
   the viewer animates in. No match after that → the answer is still rendering;
   back to step 1.
4. **Click and give the download real time.** Record `t0`, `click` the matched
   ref, then poll `~/Downloads/Gemini_Generated_Image_*` once a second for up to
   25s for a file newer than `t0`. The original is a multi-megabyte PNG and takes
   11–17s; a six-second wait is what sent every row to the low-res fallback while
   reporting nothing wrong. The click reports success even when the browser
   refuses the download — only the file on disk is proof.
5. **Copy and clean up.** Confirm the file size is stable across a 1s recheck,
   copy the bytes to `projects/<name>/images/<row 3 filename>`, then delete
   *every* `Gemini_Generated_Image_*` newer than `t0` — one click can produce
   more than one file.
6. **Close the viewer** by matching `닫기` in a fresh `snapshot` and clicking it,
   so the tab is left as it was found and the next probe is not blocked.
7. **Fallback only if no file landed:** `evaluate` `CANVAS_JS`, then pull
   `window.__pptMasterGrab` in 600,000-char slices and base64-decode. This is the
   displayed 1024px copy, and it must be reported as such.
8. **Write the manifest myself**, because no script did: set row 3's
   `status = "Generated"`, delete `last_error`, delete `slot`, write the file
   back immediately, then run §6 in full — including the ratio check, which the
   hand path does not do for me.
