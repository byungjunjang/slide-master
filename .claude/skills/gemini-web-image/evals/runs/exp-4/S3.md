# S3 — Execution plan: fill the manifest while the WebBridge daemon is refusing connections

Scenario: the user asks me to fill `image_prompts.json`'s `ai` rows through this
skill. A POST to `http://127.0.0.1:10086/command` returns nothing — connection
refused.

Route is already settled by the caller (a manifest with non-`Generated` `ai` rows
on a host with no usable CLI/API image backend). This plan does not re-decide the
route; it decides what happens to *this* run given the daemon state.

---

## Step 1 — Run the preconditions gate in order (SKILL.md §2)

The gate is ordered, and check 1 is the daemon. Nothing below check 1 matters
until check 1 passes, because every later check is either performed through the
bridge or is only meaningful once the bridge can act.

| # | Precondition | How it is decided | State right now |
|---|---|---|---|
| 1 | WebBridge daemon | `list_tabs` on any session returns `"ok": true` | **FAILED** — the daemon's endpoint refuses the connection |
| 2 | Gemini signed in | account chip renders on `gemini.google.com` | not reached |
| 3 | Browser UI in Korean | the accessible names the script matches (`Gemini 프롬프트 입력`, `메시지 보내기`, `사용해 보기`, `원본 크기 이미지 다운로드`, `닫기`) exist on a live page | not reached |
| 4 | Manifest valid, ≥1 non-`Generated` row | read the manifest | not reached |
| 5 | Downloads land silently (optional) | `gemini.google.com` allowed under automatic downloads | not reached |

### What the observed curl result maps onto in the script

`scripts/gemini_web_image.py` performs exactly this check as its first real
action, before it reads anything:

- `main()` → `require_daemon()` → `call("list_tabs", {}, "ppt-master-image")`
- `call()` shells out to `curl -s -m 120 -X POST http://127.0.0.1:10086/command …`
- connection refused ⇒ empty stdout ⇒ `json.loads("")` raises `JSONDecodeError`
  ⇒ `call()` returns `{"ok": False, "error": {"message": ""}}`
- `require_daemon()` raises: *"Kimi WebBridge is not answering on
  127.0.0.1:10086. Start the daemon and confirm the browser extension is
  connected, then rerun."*

So the script's own verdict is already known, and it is the same verdict the
§2 gate reaches. Note the ordering consequence: `require_daemon()` runs *before*
`manifest_path.read_text()`, so a run in this state never opens the manifest,
never validates it, and never writes to it.

### Decision point A — is this a failed precondition or a transient blip?

I check **what kind of failure the transport reported**, not just that it failed:

- **Connection refused** (this scenario): nothing is listening on port 10086.
  That is a process-not-running signal, not a slow-answer signal. → **Failed
  precondition. Stop.** This is the branch taken.
- Had it instead been a curl timeout, a hang, or a 200 with malformed JSON, that
  would be a daemon that *is* listening but is wedged or mid-restart — I would
  re-issue the single `list_tabs` check once before deciding, since the skill
  already treats one transport blip as retryable elsewhere (`submit()` retries a
  failed `navigate` once after a 2s pause). Repeated failure lands on the same
  stop.
- Nothing in SKILL.md or the script authorizes a retry loop, a backoff, or
  starting the daemon myself. There is no documented start command in either
  file, so I do not invent one.

### Decision point B — do I run the script anyway, to let the tool speak?

Both branches end in the same stop, so this is a cost question:

- **Branch taken: do not run it.** The evidence in hand already answers the one
  question `require_daemon()` asks, and running it produces an unhandled
  `RuntimeError` traceback rather than a cleaner message than I can already
  quote. It would also not reach the manifest, so it would not tell me anything
  about row state.
- If the user asks for the tool's own output, running
  `python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py --manifest <manifest>`
  once is harmless — it dies at the gate with no side effects.

## Step 2 — Things I explicitly do not do here

Each of these is a plausible-looking workaround that the two authoritative files
rule out:

1. **No fallback to another image path.** SKILL.md §2: "Do not fall back to
   another image path from inside this skill — that decision belongs to the
   caller." So no `image_gen.py` CLI/API backend, no `agy`, no `codex`, no
   hand-written prompts to some other generator. I surface the failure and let
   the caller choose.
2. **No hand-driving the browser around the daemon.** The bridge *is* the
   daemon; every action this skill performs (`navigate`, `snapshot`, `fill`,
   `click`, `evaluate`, `list_tabs`, `close_tab`) is a POST to that endpoint.
   With it refused there is no degraded mode to fall back into, and improvising
   a manual Gemini session by hand is outside the contract this skill executes
   (it would also produce no `slot` bookkeeping, so a later `--collect-only`
   could not find anything).
3. **No `--collect-only` rescue attempt.** `--collect-only` skips submission,
   not the daemon: `require_daemon()` runs before the `args.collect_only`
   branch, and collection itself is `evaluate(READY_JS, slot_name(index))` per
   slot — pure bridge traffic. Tabs left open from an earlier run are
   unreachable while the daemon is down.
4. **No `--displayed-size`, no lowered `--batch`, no raised `--deadline`.**
   Those tune generation cost; none of them touches the transport.
5. **No `find_tab`, ever** (SKILL.md §4) — not now, not in the resumed run.
6. **No editing the manifest by hand.** The script owns `status`, `slot`, and
   `last_error`, and it never reached the manifest, so nothing was attempted and
   nothing failed at row level. Rows stay exactly as they are — `Pending` /
   `Failed` with whatever `last_error` they already carried. Writing a
   `last_error` myself would falsely record a Gemini attempt that never
   happened. The manifest is left byte-identical.

## Step 3 — What I report back

Name the failed precondition, in these terms:

- **Precondition 1 (WebBridge daemon) failed.** `127.0.0.1:10086` refused the
  connection, so `list_tabs` cannot return `"ok": true`. Everything this skill
  does goes through that endpoint.
- **Remedy, quoted from the script's own gate:** start the Kimi WebBridge daemon
  and confirm the browser extension is connected, then rerun. (Two separate
  things: a daemon that is up but whose extension is not connected will answer
  the port; a refused connection means the daemon process itself is not
  listening.)
- **No rows were attempted.** The manifest is untouched; `0` images generated;
  no tabs opened; no tab groups created.
- **The rerun command**, with the user's actual manifest path substituted:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

- **The open decision is the caller's**: wait for the daemon, or route these
  rows to a different image backend. I state the choice; I do not take it.

## Step 4 — Contingent resumption (only after the user reports the daemon is up)

Nothing in this step runs until Decision point A flips. If the user comes back
with "daemon started", I restart at the top of the gate rather than assuming the
rest of §2 still holds — the browser may have been restarted along with it.

**4.1 Re-verify preconditions 1–5.**
- 1: `list_tabs` on session `ppt-master-image` → expect `"ok": true`. Still
  refused ⇒ back to Step 3, unchanged.
- 2/3: on the signed-in Gemini page, confirm the account chip and that the
  Korean accessible names are the ones actually rendered. A non-Korean UI and a
  signed-out session both surface later as "prompt box never appeared", so they
  get checked *before* the run, not diagnosed from the log.
- 4: read the manifest; count rows with `status != "Generated"`; note which of
  those already carry an integer `slot`.

**4.2 Decide submit vs collect.**
- Any pending row carrying an integer `slot` **and** its tab still open (checked
  with `list_tabs` on `ppt-master-image-<slot+1>`, never `find_tab`) ⇒ run with
  `--collect-only` first, so a finished image is read instead of regenerated.
- Pending rows with **no** `slot` ⇒ they are submitted, never guessed into a
  slot number (SKILL.md §4: re-numbering survivors saves one row's image under
  another row's name).
- Daemon was down through a browser restart, so tabs are gone ⇒ plain submit run
  for everything pending.

**4.3 Size the pass.**
- Submit the whole set in one pass; splitting only repeats the submission cost.
- The two files disagree on `--batch` / `--generate-wait` defaults (SKILL.md §3
  says 4 / 25; the script's `argparse` says 10 / 10). The script is what
  executes, so I pass them explicitly rather than relying on either default.
- ~220s of the 300s default deadline is serial work for ten rows (≈10s submit +
  ≈12s original download each), so for more than ~8 pending rows I either raise
  `--deadline` or take `--displayed-size` — and I say which trade I made.

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json \
  --batch 10 --generate-wait 10 --deadline 300
```

**4.4 Say the clutter out loud at submit time.** N rows leave N Chrome tab
groups titled `agent:ppt-master-image-1 … -N`; that is the cost of one session
per row. Offer `close_tab` per slot session afterwards — and not before every
row reads `Generated`, since a `--collect-only` rerun needs those tabs.

**4.5 Read the log for these specific lines and branch on each.**

| Log line | Meaning | Branch |
|---|---|---|
| `prompt box never appeared` on every row | check the tab's **URL** first | `google.com/sorry/index` ⇒ Google's unusual-traffic challenge: stop, tell the user, do not attempt the challenge. Otherwise ⇒ signed out or non-Korean UI (precondition 2/3) |
| `send never took … leaving it Pending` | the send was dropped after one resend | leave `Pending`, resubmit in a later pass |
| `no answer started — dropping it` | blank conversation past the 75s grace | resubmit that row; do not keep sweeping it |
| `original file via the viewer download` | the viewer step worked; original size | expected path |
| `viewer download did not produce a file …` | fallback latched on for the **rest of the run** — every later row lands at 1024px | note which rows saved after this line and resubmit them once downloads work, rather than accepting the low-resolution copies silently |
| `** ratio off, review this row` | drift > 4% from `aspect_ratio` | resubmit that row; it is not a footnote |
| `not ready before the deadline — left Pending` | budget expired | rerun with `--collect-only` (slots are recorded in the manifest) before considering a resubmit |
| final `OVER the …s deadline` / `over budget` | run exceeded its wall clock | attribute per row using the `gemini done at …s, lag …s` figures: large lag = detection on our side, large `gemini done` = generation on theirs |

**4.6 Verify before reporting success (SKILL.md §5).**
1. Every requested row reads `Generated` and its file exists on disk.
2. Each file's ratio is within 4% of its row's `aspect_ratio`.
3. No two output files share a checksum — identical files mean slot isolation
   broke and the run is redone:

```bash
shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
```

4. `~/Downloads` holds no leftover `Gemini_Generated_Image_*`.

**4.7 Hand back what is left.** Rows this skill could not finish stay `Pending`
with their `last_error`; the manifest is the record, and the caller decides
whether to rerun here or route them elsewhere.
