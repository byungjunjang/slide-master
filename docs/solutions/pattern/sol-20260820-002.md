## Problem

The browser image path tried the page's download control for the original file
and fell back to reading the rendered `<img>` off a canvas when that did not
produce a file. The fallback worked. Every run finished, every row reported
`Generated`, every checksum was distinct, every aspect ratio was within
tolerance — and every image was 1024px instead of 2752px, a 2.7× linear loss on
a whole deck.

Nothing ever failed, so nothing was ever diagnosed. The run log said `download
refused` once and then suppressed the attempt for the remainder of the run,
which read as a settled environmental fact rather than an open question. It was
attributed to Chrome blocking automatic downloads and left there for an entire
session, through several deck builds.

There were two causes, and both were invisible behind the fallback:

1. **The control does not exist where it was being looked for.** The result
   `<img>` sits inside a `<button class="image-button">`; clicking that opens a
   viewer, and only inside the viewer do the share / copy / download-original
   controls render. The code searched the accessibility tree of the inline
   result, which never contains them.
2. **A wait tuned for the wrong thing.** The original is a multi-megabyte PNG
   and takes 11–17s from click to file. In the middle of a speed pass the wait
   had been cut from 10s to 6s — an "optimization" that guaranteed the fallback
   on every row while looking like a saving.

## Solution

Open the viewer first, poll briefly for the control, click, allow real time for
a large file, and close the viewer so the tab is left as it was found. Then make
the two outcomes distinguishable in the log:

```
original file via the viewer download (13s)      ← the intended path
viewer download did not produce a file; ...      ← the fallback, and why
```

The skill's failure table now keys on that distinction rather than on the
symptom: *every row lands at 1024px* means the viewer step failed, not that the
browser refused anything.

## Key Insight

A fallback converts a defect into a quality regression, and quality regressions
do not page anyone. The more robust the fallback, the longer the defect survives
— and the more confident the run's output looks while it does.

Two habits follow. Log which branch ran, every time, at the level where someone
reads it; a fallback that is silent when taken is indistinguishable from a
primary path that works. And when a run consistently takes the fallback, treat
the consistency itself as the finding: "it always falls back" is not an
environment, it is an unexamined bug.

The corollary bites hardest during optimization. Shaving a timeout that only
guards the primary path is invisible in every success metric — the run gets
faster and still reports success — while quietly routing all output through the
degraded branch.

## Context

`.claude/skills/gemini-web-image/scripts/gemini_web_image.py` `export_to()`.
Found only because the user pushed on image quality directly; no automated
check in the project would have caught it, since resolution was never asserted
against anything. Measured recovery: 16:9 went 1024×572 (32 KB) → 2752×1536
(4.3 MB); 1:1 went 1024×1024 → 2048×2048.

### Reinforced 2026-08-20 — the fix carried the same shape

The repair above introduced a run-wide latch: once the viewer download failed,
`_download_refused` stayed set and every later row took the canvas copy without
trying. That is defensible when the browser really is refusing downloads, and it
was written for exactly that case — but it fired on any failure, including a
viewer that simply did not open on one row. One bad moment demoted the rest of
the deck to 1024px, and the log said so once, at the top, where a reader
scanning the tail of a successful run would never look.

Seven agents reading the skill cold found it independently; none of the
project's own checks could, because resolution is still not asserted anywhere.

Two changes followed, and the second matters more than the first:

- Latch only on evidence of the thing being latched. A click that produced no
  file proves refusal. A viewer that never opened proves nothing about the
  browser, so that row falls back alone and the next row still tries.
- **Report the degradation at the end, where the verdict is read**, naming every
  row that fell back:

```
** 3 of 10 row(s) fell back to the 1024px rendered copy instead of the original: a.png, b.png, c.png
```

The original lesson was "log which branch ran". The sharper version is: log it
where someone forms their conclusion about the run. A line at the top of a
four-minute log is not that place.
