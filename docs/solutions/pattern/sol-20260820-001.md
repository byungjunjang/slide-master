## Problem

A ten-image run through the Gemini web app took 10m29s. Its log showed a probe
firing every ten seconds and reporting "still generating" for 445 consecutive
seconds before the first file appeared. From that I concluded Gemini needed
7m24s to return one image under ten-way concurrency, and from *that* I concluded
concurrency was the binding constraint and lowered the default batch size.

Every step of that reasoning was wrong, and the error was invisible because the
polling interval was tight. Ten seconds cannot hide seven minutes — so the
number looked well-measured.

The probe itself was broken. It judged readiness by `img.naturalWidth > 300`,
and the result element is routinely laid out at zero size, where a lazy image
never decodes. A finished image reported as unfinished, indefinitely. Four rows
in that same run demonstrably hit it. The tell, which I missed, was in the log:
six saves landed in three consecutive sweeps rather than spread across the
window — a detection cascade, not six independent completions.

Measured after the fix, a single image takes about 25–30 seconds.

## Solution

Make the probe report two facts instead of one, and log both plus their
difference on every completed item:

```js
const creating = document.body.innerText.includes('Creating your image');
return JSON.stringify({
  present: !!img,
  creating: creating,
  finished: !!img && !creating,          // their clock: the answer stopped rendering
  decoded: !!img && img.complete && img.naturalWidth > 300   // ours: bytes readable
});
```

```
saved t10_6.png ... [sweep 36, read at 187s, gemini done at 180s, lag 7s]
```

That one line settles attribution permanently. A large `finished` time is the
external system being slow. A large lag is this code being blind. The very next
run used it to prove a 180-second outlier was genuinely Gemini's, which the old
instrumentation could never have established.

## Key Insight

A single-signal readiness probe cannot distinguish "not done yet" from "done,
but I cannot see it" — and the failure is asymmetric: your bug always presents
as their latency, never the reverse. So the number you publish is inflated by
exactly the amount you are broken, and it looks like a clean measurement.

Before quoting a latency for anything you poll, ask what the probe would report
if the work had finished and the probe were wrong. If the answer is "the same
thing it reports now", the number is an upper bound, not a measurement, and any
design built on it is built on your own defect.

Instrument the boundary, not just the outcome: one clock for when the other side
finished, one for when you noticed, and the gap between them recorded.
