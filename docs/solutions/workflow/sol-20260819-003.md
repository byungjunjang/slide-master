## Problem

A skill was scored by having agents read it and write the execution plan they
would follow, then grepping those plans for rules. The suite reached 100% and
stayed there across three rounds while real defects were still in the code —
including one that would write another row's image under a row's file name, the
exact failure class the suite was built to catch.

Binary checks can only ask what their author already knows to ask. Once the
known failures are covered, the score stops moving and stops informing.

## Solution

Two changes, and the second is the one that mattered.

**One agent per scenario, not one agent per batch.** Batching several scenarios
into one agent correlates their plans — a single misreading fails all of them —
and leaves only the first a genuine cold read, which is the condition being
measured. Splitting them did not move the score at all, which retired the worry
that the earlier figure was inflated.

**Read the plans, not only the tally.** Seven readers coming to the skill cold
reported three defects no check was asking about: a slot number recomputed after
a process restart so it pointed at another row's tab, a timeout the prose and
the code disagreed on, and a row dropped from a retry sweep. All three were real
and all three were fixed.

## Key Insight

A grep over free prose scores phrasing as much as understanding. Every failure
that suite ever reported turned out to be the checker's fault, not the skill's —
three separate calibration rounds — so a failing check means *read the plan
first*, and only then consider changing what is being tested.

The corollary is more useful: when the score saturates, that is the signal to
start harvesting what the readers noticed rather than to add checks or declare
victory. Treat 100% as the floor of a round's value.

## Context

Measured on `.claude/skills/gemini-web-image` and its `evals/` suite. The
harness records the one-agent-per-scenario rule and the read-the-plan caution.
